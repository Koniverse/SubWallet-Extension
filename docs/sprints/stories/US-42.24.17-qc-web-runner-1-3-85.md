## Goal

Check the signing prompt security fix, on Android and iOS, on a fresh install and on an upgrade. The AC were written out on 2026-09-15 from the polkadot-js report behind the issue, taking the story from 7 AC to 11.

Parent: [US-42.24](US-42.24-qc-web-runner-1-3-86.md).

## What is in this version

Signing prompts could conceal the actual transaction ([#5042](https://github.com/Koniverse/SubWallet-Extension/issues/5042)) — a security fix following the same problem [reported by the polkadot-js extension team](https://forum.polkadot.network/t/update-polkadot-js-extension-to-0-64-0-signing-prompts-could-hide-the-real-transaction/18291). A signing request could be crafted so the prompt showed something other than what was really being signed.

This is a security check, not a display check. The point is that what the user sees on the signing screen is what actually gets signed.

The issue body is one sentence, so the AC below were written on 2026-09-15 from the polkadot-js report it links to, which describes the attack and what the fix changes.

The same fix was QC'd on Extension in [US-42.11](US-42.11-qc-extension-pr5043-and-issue5045.md) and on Web App in [US-42.12](US-42.12-qc-webapp-pr5043-signing-prompt-security.md), both passing with no bug. A UI problem was raised in the second comment on #5042 on 2026-08-05, but the third comment three hours later carried a new build for fresh install and upgrade, and both stories passed on it — so nothing is carried into this one. Mobile runs the same Extension code through the web-runner, so the checks are the same; what differs is reaching the signing screen from the in-app browser or WalletConnect rather than a browser extension.

## Before testing

- A dApp, or a test page, that can send a request down the extrinsic channel with a payload shaped like a raw message. Without this the fix cannot be tested at all — this is the whole setup cost of the story. The polkadot-js report describes the payload shape.
- A way to see what was actually signed, not only what the prompt showed, so AC-2 can be checked rather than assumed.
- WalletConnect or the in-app browser working, to reach the signing screen from outside.
- The previous web-runner version installed, with accounts and data, for the upgrade runs.

## Things to check

The attack, from the polkadot-js report

A dApp sends its request down the extrinsic channel — the one used for transactions — but shapes the payload so it looks like a raw message. The old code decided how to sign from the channel and what to show from the payload, so the two could disagree: the wallet signed a transaction while the prompt showed an off-chain message with no method, destination or amount. The raw-message channel was never the way in, because it wraps what it signs in a `<Bytes>` envelope that cannot be read back as a transaction. The fix makes the channel an explicit field rather than something inferred from the payload, and the extrinsic channel now rejects a payload dressed as a raw message before any prompt is drawn.

The check that matters

- [ ] AC-1: A transaction request sent down the extrinsic channel but shaped to look like a raw message is refused before any prompt appears — nothing is drawn for the user to approve — Android + iOS fresh — skipped, cannot be tested on Mobile
- [ ] AC-1a: The refusal says something the user can act on, rather than failing silently or looking like a network error — Android + iOS fresh — skipped, cannot be tested on Mobile
- [ ] AC-1b: Refusing it leaves the wallet usable — the dApp connection survives and the next, honest request from the same dApp still works — Android + iOS fresh — skipped, cannot be tested on Mobile

The prompt tells the truth

- [ ] AC-2: A normal transaction request shows the right details — method, destination, amount, network and fee — and signing it produces that transaction and no other — Android + iOS fresh — skipped, cannot be tested on Mobile
- [ ] AC-3: Signing a message, as opposed to a transaction, shows the real message content and is signed as a message — Android + iOS fresh — skipped, cannot be tested on Mobile
- [ ] AC-3a: A raw-message request is wrapped in the `<Bytes>` envelope, so what gets signed cannot be replayed as a transaction — Android + iOS fresh — skipped, cannot be tested on Mobile
- [ ] AC-4: A request the app cannot decode safely is refused or clearly flagged, rather than shown as if it were understood — Android + iOS fresh — skipped, cannot be tested on Mobile

Nothing honest is broken

- [ ] AC-5: Ordinary dApp signing still works and is not blocked by the fix — both transactions and messages, on the in-app browser and through WalletConnect — Android + iOS fresh — skipped, cannot be tested on Mobile
- [ ] AC-5a: Signing from a QR account still works, where the payload goes out to another device and comes back — Android + iOS fresh — skipped, cannot be tested on Mobile

Upgrade

- [ ] AC-6: AC-1 to AC-5a pass on Android + iOS upgrade — skipped, cannot be tested on Mobile
- [ ] AC-7: After upgrading, existing dApp connections still work and their signing requests are shown correctly — both platforms — skipped, cannot be tested on Mobile

## Bugs found

None. Nothing was run, so nothing was found.

## Test notes

Closed on 2026-09-15 without being run. None of the 11 AC could be tested on Mobile.

The fix is in the signing layer, and reaching it needs a dApp or test page that sends a request down the extrinsic channel with a raw-message-shaped payload. That setup could not be put together against the Mobile build, so every AC is skipped rather than failed — nothing here says the fix is broken, only that this platform could not check it.

The same fix was tested and passed elsewhere: [US-42.11](US-42.11-qc-extension-pr5043-and-issue5045.md) on Extension, 7 of 7 AC, and [US-42.12](US-42.12-qc-webapp-pr5043-signing-prompt-security.md) on Web App, 5 of 5 AC, both with no bug. Mobile runs the same Extension code through the web-runner, so the fix itself reached this build; what is missing is the evidence from this platform.

If a test harness for crafted signing requests becomes available, this story is the one to reopen.
