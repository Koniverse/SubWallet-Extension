## Goal

Show the unstaking window the chain will actually enforce. Where a runtime exposes a shorter
unbonding period for nominators who cannot be slashed, relay-chain native staking and nomination
pools must read *that* period — not the general `bondingDuration` — so the wait a user is quoted
before unstaking is the wait they get.

## Background

Tracked as [#5055](https://github.com/Koniverse/SubWallet-Extension/issues/5055) —
*"Update nominator unstaking eras"*. On Polkadot the practical effect is the headline number: the
withdraw wait on DOT drops from **28 days to 2**.

Every relay-chain unstaking figure in the wallet came from one expression:

```ts
const unlockingEras = substrateApi.api.consts.staking.bondingDuration.toString();
```

`bondingDuration` is the *slashing-era* window — how long stake must stay exposed for a slash to
still reach it. When the runtime carries `staking.nominatorFastUnbondDuration` **and**
`staking.areNominatorsSlashable` reads `false`, that exposure does not apply to nominators and the
runtime lets them unbond on the shorter clock. The wallet kept quoting the long one, so the
countdown, the "withdraw available in" label and the unstake confirmation were all wrong by
26 days on Polkadot — in the direction that makes the product look worse than it is.

The fix is one helper, `getNominatorUnstakingEras()`, and four call sites that now await it.
The helper is deliberately conservative: **both** conditions must hold before it returns the fast
duration, and any chain that exposes neither const falls through to `bondingDuration` unchanged.

### Why this is a new story and not a row in an existing one

[Rule 9](../../../AGENTS.md) — *new work is a new story, not a new row*. The two capabilities this
touches shipped years ago and their incremental tables are records of what they delivered:

- **[US-12.1](US-12.1-native-nomination-staking-relay-and-parachains.md)** (FR-114) owns the relay
  native-staking handler, `done` @ 0.4.7.
- **[US-12.2](US-12.2-nomination-pool-staking.md)** (FR-115) owns `NominationPoolHandler`,
  `done` @ 1.0.1.

Neither materializes a new requirement here and the change spans both, so appending a row to
either would split one fix across two shipped stories and claim it for the wrong window. This
story **defends** FR-114 and FR-115 rather than owning them ([rule 8](../../../AGENTS.md)); both
keep their single owner in [EPIC-12](../epics/EPIC-12.md)'s FR Coverage table.

## Acceptance criteria

- [x] **AC-1** — **Given** a runtime that exposes `staking.nominatorFastUnbondDuration` **and**
  reports `staking.areNominatorsSlashable() === false`, **When** `getNominatorUnstakingEras(api)`
  is called, **Then** it returns the **fast** duration. *(Both conditions are one `&&` chain; the
  slashable query is awaited and string-compared to `'false'`.)*
- [x] **AC-2** — **Given** a runtime missing either signal, **When** the same helper is called,
  **Then** it returns `bondingDuration` — the pre-existing behaviour, unchanged. *(The `return
  api.consts.staking.bondingDuration.toString()` fallthrough is the function's last statement.)*
- [x] **AC-3** — **Given** the helper exists, **When** the codebase is searched for direct
  `bondingDuration` reads, **Then** **exactly one** remains and it is the fallback inside the
  helper itself. *(No unstaking-period path can bypass the check by construction — this is the AC
  that would catch a fifth call site being added later against the old expression.)*
- [x] **AC-4** — **Given** a nomination-pool position on a fast-unbond chain, **When**
  `NominationPoolHandler` builds its pool metadata, **Then** `unlockingEras` comes from the helper.
  *(FR-115; `nomination-pool/index.ts:112`.)*
- [x] **AC-5** — **Given** a relay-chain native-staking position, **When**
  `RelayNativeStakingPoolHandler` builds its metadata, **Then** `unlockingEras` comes from the
  helper. *(FR-114; `native-staking/relay-chain.ts:82`.)*
- [x] **AC-6** — **Given** the pre-EarningService relay-chain metadata path is still live, **When**
  either of its two entry points runs, **Then** both read through the helper. *(`relayChain.ts:131`
  in `subscribeRelayChainStakingMetadata` and `:184` in `getRelayChainStakingMetadata` — the
  subscription and the one-shot. Missing one leaves a screen that disagrees with its own refresh.)*

## Changelog entry

### Changed

- Read the nominator unstaking period from `nominatorFastUnbondDuration` when nominators are not
  slashable, so relay-chain native staking and nomination pools show the fast unbonding window
  instead of `bondingDuration` — 2 days rather than 28 on Polkadot (#5055, US-12.22)

## Open — no unit test guards the branch

The helper has two branches and a runtime-shape precondition, and **nothing in the unit suite
exercises either**. Every AC above is a static claim about the code; none of them would survive
someone inverting the `=== 'false'` comparison, which is the single most likely way this breaks.
The behaviour was verified by hand — [US-42.14](US-42.14-qc-issue-5055-nominator-unstaking-eras-dot-2-days.md)
passed 6/6 on Extension across fresh install and upgrade — so the fix is *checked*, but only
once, by a person, against one chain.

A mocked-`api` spec asserting both branches would cost little and is the shape
[US-5.15](US-5.15-signing-prompt-mode-confusion.md) already set for this repo
(`RequestExtrinsicSign.spec.ts`). **Recommended, not taken here** — adding a test is new work and
belongs in the sprint that picks it up ([rule 9](../../../AGENTS.md)), not appended to a story
that shipped without one.
