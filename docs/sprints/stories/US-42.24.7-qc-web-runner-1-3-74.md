## Goal

Check multisig account phase 1 — creating a multisig account, seeing pending requests, and approving them — on Android and iOS, on a fresh install and on an upgrade.

Parent: [US-42.24](US-42.24-qc-web-runner-1-3-86.md).

## What is in this version

Multisig account phase 1, the UI part ([#4855](https://github.com/Koniverse/SubWallet-Extension/issues/4855)).

The issue body is an unfilled GitHub template — no description, no acceptance criteria. The AC below were rewritten on 2026-09-08 from the multisig QC checklist instead, which is where the real scope is.

A multisig account is one address controlled by several signatories, where a set number of them have to approve before a transaction goes through. Phase 1 is far wider than creating one: it reaches the export list, the signatory picker inside every feature that signs, notifications, history, and the behaviour when a signatory or the multisig itself is deleted.

## Before testing

- Accounts of every signatory kind: normal, QR, watch-only, ledger, proxy, and another multisig account.
- Funds on the multisig address, so a transaction can actually be submitted and approved.
- An existing staking position and an earning position, for the signatory checks in those flows.
- A dApp to try connecting from, to confirm a multisig account is refused.
- The previous web-runner version installed, with accounts and data, for the upgrade runs.

Setting up multisigs with each kind of signatory, then walking a transaction through each of them, is most of the effort here. The delete cases need a second multisig so that one can be removed while another still holds pending transactions.

## Things to check

These follow the multisig QC checklist rather than [#4855](https://github.com/Koniverse/SubWallet-Extension/issues/4855), whose body is an unfilled template. The checklist covers seven areas: creating an account, managing it, export and reimport, choosing a signatory inside each feature, notifications, history, and the multisig tab on a single-chain transfer. Only the main cases are written here; the narrower variants are run against the checklist itself.

Creating a multisig account

- [x] AC-1: A multisig account can be created by picking signatories and a threshold, and the address matches what the chain derives — Android + iOS fresh
- [x] AC-2: The threshold field refuses to go past the number of signatories and refuses to be left empty — Android + iOS fresh
- [x] AC-3: Signatories of each kind can be added — normal, QR, watch-only, ledger, proxy and another multisig — Android + iOS fresh
- [x] AC-4: The multisig account appears in the account list marked as multisig, and its balance loads — Android + iOS fresh

Managing a multisig account

- [x] AC-5: The signatory list and threshold can be seen after creation, and the account can be renamed and removed — Android + iOS fresh
- [x] AC-6: When a multisig account has no signable signatory left, because the signatories were deleted, it behaves as watch-only, and sending from it gives "No signatories/proxies found to sign this multisig transaction. Add signatories/proxies and try again" — Android + iOS fresh

Export and reimport

- [x] AC-7: Multisig accounts appear in the export account list and export all, and a multisig account can be exported on its own — Android + iOS fresh
- [x] AC-8: A multisig account can be imported back from the exported JSON file — Android + iOS fresh
- [x] AC-9: Recreating a deleted multisig with the same signatories and threshold restores the old account, for signatory lists of each kind — normal, QR, watch-only, ledger, proxy and multisig — Android + iOS fresh
- [x] AC-10: A restored multisig keeps its history and notifications, and its actions can be performed again — Android + iOS fresh

Choosing a signatory inside each feature

- [ ] AC-11: Transfer on a single chain — a multisig with at least two signable signatories can transfer, and the signatory picker behaves as designed — Android + iOS fresh
- [ ] AC-12: Transfer max — transfer all equals the transferable amount, and when the fee is paid in the native token the signatory paying it is shown — Android + iOS fresh
- [ ] AC-13: Cross-chain transfer follows the same signatory logic — Android + iOS fresh
- [ ] AC-14: Swap is disabled for a multisig account, both with and without XCM — Android + iOS fresh — fail: BUG-42.24.7-10
- [ ] AC-15: Earning — nomination pool and direct nomination follow the transfer logic; liquid staking and subnet staking are hidden — Android + iOS fresh — fail: BUG-42.24.7-11
- [ ] AC-16: Unstake, stake more, withdraw and change validator all follow the same logic — Android + iOS fresh
- [ ] AC-17: A multisig account cannot connect to a dApp and cannot sign for one — Android + iOS fresh
- [ ] AC-18: Buy token is unaffected, and adding or removing a proxy follows the transfer logic — Android + iOS fresh

Notifications

- [ ] AC-19: The All tab holds no multisig items, while the multisig tab shows them with icon, time, account name, action title and content — Android + iOS fresh
- [ ] AC-20: The unread and read tabs behave as before and exclude multisig items — Android + iOS fresh
- [ ] AC-21: Search works on the multisig tab, and the empty state shows when nothing matches — Android + iOS fresh

History

- [ ] AC-22: The transaction tab shows ordinary transactions and no pending or completed multisig ones, and after a multisig submission the init, execute, approve and reject records appear — Android + iOS fresh
- [ ] AC-23: The multisig tab shows pending transactions as waiting for approval or approved, and they disappear once the threshold is met — Android + iOS fresh
- [ ] AC-24: In account detail the same holds per account, whether the account is viewed as the multisig or as one of its signatories — Android + iOS fresh
- [ ] AC-25: Deleting a signatory hides its pending transactions from the multisig tab; deleting the multisig itself keeps them but shows the address in place of the name — Android + iOS fresh

The multisig tab on a single-chain transfer

- [ ] AC-26: A pending record appears on the multisig tab whatever kind the signatories are — normal, QR, ledger, proxy, multisig — Android + iOS fresh
- [ ] AC-27: With a watch-only signatory, applying gives "The account you are using is Watch-only account, you cannot use this feature with it" — Android + iOS fresh
- [ ] AC-28: Opening a pending transaction offers the right actions for who is looking: the initiator can reject, an in-between signatory can approve, the last signatory with call data can approve and execute — Android + iOS fresh
- [ ] AC-29: A completed transaction offers view on explorer, and it opens that transaction on Subscan — Android + iOS fresh
- [ ] AC-30: Reject, approve, and approve and execute each open their own confirmation screen — Android + iOS fresh

On upgrade

- [ ] AC-31: AC-1 to AC-30 pass on Android + iOS upgrade
- [ ] AC-32: After upgrading, multisig accounts, their pending transactions and their notifications are all still there and still correct — both platforms
