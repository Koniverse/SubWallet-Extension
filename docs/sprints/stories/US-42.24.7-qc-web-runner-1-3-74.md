## Goal

Check multisig account phase 1 — creating a multisig account, seeing pending requests, and approving them — on Android and iOS, on a fresh install and on an upgrade.

Parent: [US-42.24](US-42.24-qc-web-runner-1-3-86.md).

## What is in this version

Multisig account phase 1, the UI part ([#4855](https://github.com/Koniverse/SubWallet-Extension/issues/4855)).

The issue body is an unfilled GitHub template — no description, no acceptance criteria. The AC below were rewritten on 2026-09-08 from the multisig QC checklist instead, which is where the real scope is.

A multisig account is one address controlled by several signatories, where a set number of them have to approve before a transaction goes through. Phase 1 is far wider than creating one: it reaches the export list, the signatory picker inside every feature that signs, notifications, history, and the behaviour when a signatory or the multisig itself is deleted.

## Before testing

- Accounts of every signatory kind: normal, QR, watch-only, ledger, proxy, and another multisig account.
- Funds on the multisig address, so a transaction can actually be submitted and approved.
- An existing staking position and an earning position, for the signatory checks in those flows.
- A dApp to try connecting from, to confirm a multisig account is refused.
- The previous web-runner version installed, with accounts and data, for the upgrade runs.

Setting up multisigs with each kind of signatory, then walking a transaction through each of them, is most of the effort here. The delete cases need a second multisig so that one can be removed while another still holds pending transactions.

## Things to check

These follow the multisig QC checklist rather than [#4855](https://github.com/Koniverse/SubWallet-Extension/issues/4855), whose body is an unfilled template. The checklist covers seven areas: creating an account, managing it, export and reimport, choosing a signatory inside each feature, notifications, history, and the multisig tab on a single-chain transfer. Only the main cases are written here; the narrower variants are run against the checklist itself.

## Test notes

- Tested 2026-09-09, 2026-09-10 and 2026-09-11 — Mobile, Android and iOS, fresh install and upgrade
- Passed: 28 of 32
- Failed: AC-13, AC-14 and AC-15, each with a bug behind it; AC-31 fails because those three fail on upgrade as well
- 28 bugs, most of them the multisig screens not matching the Extension

Four AC were corrected against the build on 2026-09-10, all four written from the checklist and all four wrong about what the app does: cross-chain is refused for a multisig rather than following the signatory logic, a multisig can connect and sign for a dApp rather than being blocked, and the All, Unread and Read tabs all hold multisig items rather than excluding them. AC-6 was corrected the same way, against the message the build actually shows. The checklist looks like an intended design the build did not follow.

The three failures are the same shape: a feature that should be closed to a multisig account is still open, or a message that should name the account names something else.

The AC were rewritten on 2026-09-08 from the multisig QC checklist. The ten they replaced came from the issue title, because #4855 has no body — they covered creating an account and approving a transaction, and said nothing about export and reimport, the signatory picker inside each feature, notifications, history, or what happens when a signatory or the multisig itself is deleted. Points went from 8 to 13 with the real scope.
