The Bittensor manual claim (#5064) was in the plan but was dropped from v1.3.89 — that issue is scheduled for a later release, so it was out of scope for this run. Its feature QC stays in [US-42.23](US-42.23-qc-issue-5064-bittensor-manual-claim.md) and carries over to whichever release picks the issue up.

Each item already has its own QC story covering the feature-level checks. This story is the release gate — it re-verified that the same content lands correctly as it moved through each build stage, plus a regression pass of the app's main functions at each stage. Both feature QC runs were done against unmerged PR builds, so this gate re-verified rather than inherited them.

One point shaped the run. #5062 is a P0 that had already stranded a real transfer, and its fix spans two repos — the ChainList data ([PR #709](https://github.com/Koniverse/SubWallet-ChainList/pull/709), merged 08-24) and the guard in PR #5063. AC-12 checked that both halves are in the build.

## Stages

1. Dev merge — merge all the issues above into the extension, then regression test on the dev environment.

3. Draft release — test the draft release build with the release content above, then regression test on a production-like build in draft form.
4. Production — after publishing, a quick recheck on the live production build.

## Regression checklist (main functions)

Run this list at each stage (dev, master, draft, production quick recheck at reduced depth):

- [x] Create a new account / import an existing account (mnemonic, private key)
- [x] Switch between accounts, view balances across chains
- [x] Unlock with the master password, and unlock with the passkey if it is on
- [x] Auto-lock triggers on time and the wallet reopens correctly
- [x] Send a native token, confirm it goes through with correct fee display
- [x] Receive a token (show/copy address, QR)
- [x] Swap tokens (at least one route)
- [x] Stake and unstake on at least one network
- [x] XCM transfer relay chain → parachain
- [x] XCM transfer parachain → parachain, with correct fee and balance update on both sides
- [x] XCM USDt Kusama Asset Hub ↔ Polkadot Asset Hub — the route is either correctly repointed and a real transfer arrives, or it is blocked outright. Tokens must not leave the source chain on a route that cannot deliver them (covers #5062, the P0)
- [x] Connect to a dApp (WalletConnect or injected), sign a message and a transaction
- [x] Export account (JSON / seed phrase) and remove account
- [x] App upgrade path: install v1.3.88, add data, upgrade to v1.3.89, confirm data, settings and the master password are preserved

## Test notes

- Tested on: dev, master build, draft release, production
- Environment: Chrome extension, fresh install and upgrade from v1.3.88; release tag `v1.3.89` (`b9363157d0`, 2026-08-28)
- Passed: 16 / 16 AC

All four stages ran and passed. The dev stage ran on 2026-08-27 against the merged code — both PRs landed that day (#5063 as `dd96d076a5`, #5061 as `82e1a09927`), so the dev result is a claim about merged code, not about the unmerged PR builds the feature QC stories used. The master, draft and production stages then re-verified the same two items on the real release build.

AC-8 holds: `package.json` at tag `v1.3.89` reads 1.3.89, and the version shown in the extension matched on both the draft and production builds.

AC-12 is signed off on both halves, and it is worth stating where each half came from because they ship from two different repos. The chainlist data fix landed in `SubWallet-ChainList` PR #709 (merged 08-24). The guard landed here in PR #5063, which touches `balance-service/transfer/xcm/utils.ts` (+164 lines), `Extension.ts`, and adds one new string to the five locale files. Neither half alone would have closed the P0 — the guard was checked against the repointed data, not on its own, and a real KAH↔PAH USDt transfer arrived rather than the route merely being blocked.

The regression checklist ran at every stage and found no new issues. The upgrade-path item, which could not run on dev because v1.3.89 did not exist yet, ran at the draft stage (TASK-42.21.13): accounts, chains, settings and the master password all carried over from v1.3.88 with no data loss. AC-9 was checked with the passkey both on and off at each stage — the master password unlocks the wallet in every combination, so the new passkey path cannot lock anyone out.
