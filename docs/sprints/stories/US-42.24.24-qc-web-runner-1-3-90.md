## Goal

Check the two items that came into the web-runner with 1.3.90, on Android and iOS, on a fresh install and on an upgrade.

Parent: [US-42.24](US-42.24-qc-web-runner-1-3-90.md).

This is the version the whole update is now named after.

## What is in this version

- sr25519 VRF signing for dApp key derivation ([#5072](https://github.com/Koniverse/SubWallet-Extension/issues/5072), [PR #5076](https://github.com/Koniverse/SubWallet-Extension/pull/5076)) — a dApp can ask the wallet to derive a key bound to its own origin. The wallet shows a Key derivation request screen and, on approval, returns a 96-byte VRF result whose first 32 bytes are the derived key.
- Manual claim for Bittensor native staking ([#5064](https://github.com/Koniverse/SubWallet-Extension/issues/5064), [PR #5065](https://github.com/Koniverse/SubWallet-Extension/pull/5065)) — root (netuid 0) positions get an unclaimed-rewards figure and a Claim button.

Both were QC'd on Extension and both passed: [US-42.25](US-42.25-qc-issue-5072-sr25519-vrf-signing.md) 11 of 11 for the VRF signing, [US-42.23](US-42.23-qc-issue-5064-bittensor-manual-claim.md) 16 of 16 for the Bittensor claim. Mobile runs the same Extension code through the web-runner, so the behaviour should match; the AC below are written from what those two runs actually checked, not from the issue titles.

Two things the Extension runs did not settle, and this story picks up.

US-42.25 never compared two origins — the test dApp was reachable at one address only — so the property the VRF feature exists for has no manual test behind it yet. AC-4 and AC-5 below do that comparison.

The Bittensor claim has a threshold below which a claim is refused, and a scale that is easy to get wrong by a factor of 2³². AC-11 and AC-13 keep both, because a wrong scale shows a plausible number rather than an error.

## Before testing

- An sr25519 account, and a dApp that calls `signVrf`. It has to be reachable from two origins for AC-4 and AC-5 — the same site at two hosts, or at `http://` and `https://`.
- A Bittensor account with a root (netuid 0) native staking position carrying unclaimed rewards, and one with rewards below the claim threshold.
- A Bittensor account with a subnet (alpha) position, to confirm no claim button appears there.
- An explorer or runtime query to read the real unclaimed figure against, rather than trusting the app's own display.
- The previous web-runner version installed, with accounts and data, for the upgrade runs.

Gathering a Bittensor root position with claimable rewards, plus a second one under the threshold, is the reason this is a 13.

## Things to check

sr25519 VRF signing ([#5072](https://github.com/Koniverse/SubWallet-Extension/issues/5072))

- [ ] AC-1: A dApp asks for a VRF signature on an sr25519 account, the Key derivation request screen appears, and approving returns a result — Android + iOS fresh
- [ ] AC-2: Rejecting the prompt returns an error to the dApp and produces no signature — Android + iOS fresh
- [ ] AC-3: Asking twice from the same site with the same data gives the same derived key — Android + iOS fresh
- [ ] AC-4: The screen shows the full origin with its scheme — `https://app.com`, not `app.com` — so the user can tell one site from another — Android + iOS fresh
- [ ] AC-5: The same dApp served from two origins derives two different keys. This is the property the feature exists for and US-42.25 could not test it — Android + iOS fresh
- [ ] AC-6: The screen names the account being used and shows the permanent-key warning — Android + iOS fresh
- [ ] AC-7: The details view shows Bound to and Context, and the values match what the dApp asked for — Android + iOS fresh
- [ ] AC-8: Ordinary dApp signing still works — connect, sign a message, sign a transaction — and a dApp that never asks for a derived key behaves exactly as before — Android + iOS fresh
- [ ] AC-9: AC-1 to AC-8 pass on Android + iOS upgrade

Bittensor manual claim ([#5064](https://github.com/Koniverse/SubWallet-Extension/issues/5064))

- [ ] AC-10: On a Bittensor root (netuid 0) position, the rewards panel shows Unclaimed rewards with a value and a working Claim button — Android + iOS fresh
- [ ] AC-11: On a Bittensor subnet (alpha) position there is no claim button and no unclaimed figure — Android + iOS fresh
- [ ] AC-12: The claim screen lists only accounts with an unclaimed reward above zero — Android + iOS fresh
- [ ] AC-13: The unclaimed figure matches the chain, read against an explorer or a runtime query rather than the app's own display, and is scaled in TAO rather than rao — Android + iOS fresh
- [ ] AC-14: A claim with one claimable validator goes through, with the right fee on the confirmation screen — Android + iOS fresh
- [ ] AC-15: A claim with several claimable validators goes through and settles all of them — Android + iOS fresh
- [ ] AC-16: After a claim the unclaimed figure drops to zero, or to the dust left under the threshold, and the staked balance reflects it — Android + iOS fresh
- [ ] AC-17: With rewards pending but all below the threshold, the claim is refused with a message naming the threshold, not a raw key — Android + iOS fresh
- [ ] AC-18: The claim appears correctly in transaction history — Android + iOS fresh
- [ ] AC-19: The root claim type removed in 1.3.86 has not come back — there is one claim path, not two — Android + iOS fresh
- [ ] AC-20: Bittensor stake, unstake and change validator all still work, since the handler was edited — Android + iOS fresh
- [ ] AC-21: AC-10 to AC-20 pass on Android + iOS upgrade

Upgrade specific

- [ ] AC-22: After upgrading, Bittensor positions and their unclaimed figures are carried over correctly, and dApp connections still work — both platforms
