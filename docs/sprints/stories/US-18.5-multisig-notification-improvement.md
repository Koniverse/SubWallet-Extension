## Goal

A multisig signatory's approval notification **survives every subscription reload and RPC failure**,
and when it no longer needs action it **says why** — approved by this signer, or no longer pending —
instead of silently disappearing and reappearing with a new timestamp.

## Background

[US-18.2](US-18.2-pending-transaction-detection-and-approval.md) shipped pending-transaction
detection at 1.3.74 — a signatory learns on-chain, without an indexer, that a transaction is waiting
for them. The notification it raises was **deleted rather than updated** whenever the subscription
re-ran, so the signal was only as stable as the last storage query. #5093 names five root causes;
the first three are the same failure wearing different clothes — *an incomplete read was treated as
proof that nothing is pending*.

## Acceptance criteria

*Read from `f836222c51`'s diff. Nothing here is inferred from the issue text alone.*

- [x] **AC-1** — An incomplete multisig storage result **no longer looks like "no pending tx"**.
  `subscribeDataWithMulti` turns an RPC error into `[]` and completes the stream; the handler now
  throws when `pendingMultisigEntries` is absent or shorter than `rawKeysArgs`, so the subscription
  resubscribes instead of clearing every notification for that multisig
  (`multisig-service/index.ts`, the guard at the top of the entry loop).
- [x] **AC-2** — A pending tx whose **extrinsic cannot be resolved keeps its last known data**
  rather than being dropped. Raw txs with no `extrinsicHash` are collected into `unresolvedTxMap`
  by call hash; their existing entry is carried forward with only `approvals` and `depositAmount`
  refreshed, and the old blanket `notifiedTxKeys.delete(key)` now runs **only** when the tx is
  genuinely gone.
- [x] **AC-3** — Notifications are **updated, not deleted**. `clearMultisigApprovalNotifications`
  is replaced by `updateMultisigApprovalNotifications`, which writes a `status` onto the
  notification metadata through the new `InappNotificationService.updateNotifications()`
  (`dbService.upsertNotifications`).
- [x] **AC-4** — The status has exactly three states, and **absent is one of them**:
  `MultisigApprovalNotificationStatus.APPROVED` (this signer has approved, others still owe),
  `RESOLVED` (the tx is off chain — executed or cancelled), and `undefined` while it still needs
  this signer. The field is optional on `MultisigApprovalNotificationMetadata`, so existing stored
  notifications read as *still waiting* rather than as an unknown state.
- [x] **AC-5** — An **unresolved** tx is never marked `RESOLVED`. When a notification's call hash is
  in `unresolvedCallHashes`, the reducer returns without touching it — *the tx is still on chain but
  its approval state cannot be verified*. This is the guard that stops AC-1's and AC-2's failure
  from re-entering through the status path.
- [x] **AC-6** — The notification screen **follows the current account**. `currentProxyId` was
  `useState(currentAccountProxy?.id)`, frozen at mount, so switching to *All accounts* on that
  screen kept refetching the account it opened with; it is now read directly from
  `currentAccountProxy?.id` (`Popup/Settings/Notifications/Notification.tsx`).
- [x] **AC-7** — A notification with a status **opens an explanation, not the history screen**.
  `onClickMultisigNotification` reads the notification fresh via `getInappNotification(item.id)`,
  and on `APPROVED` / `RESOLVED` shows an info modal; only a statusless notification navigates to
  `/home/history`.
- [x] **AC-8** — The list **re-titles** a settled notification, keeping its `[account]` prefix
  (`item.title.match(/^\[.*\]\s*/)`) and swapping title and description for the approved or
  no-longer-pending copy, so the state is visible without opening it.
- [x] **AC-9** — Clicking a statusless notification on a **disabled network** offers to enable it
  (`enableNetworkToViewMultisigTx`) instead of failing; `showActiveChainModal` now accepts
  `MULTISIG_APPROVAL` alongside `WITHDRAW` and `CLAIM` via a content map.
- [x] **AC-10** — **Absence of a tx in the background cache is not treated as proof.** After the
  chain check, the handler calls the new `getPendingMultisigTxs` message
  (`pri(multisig.getPendingMultisigTxs)`); if the tx is not there it shows *"Unable to load the
  transaction status. Please try again"* rather than claiming the tx was executed or cancelled. The
  code says so in a comment, and it is the right call — this is [LESSONS §69](../../LESSONS.md)
  applied inside the product: **an empty result is not a negative finding.**
- [x] **AC-11** — Repeat clicks cannot interleave: a `checkingMultisigNotification` ref gates the
  handler and is released in `finally`.

## Not covered

  RPC read. This is the fourth story in a row to ship without one after
  [US-12.23](US-12.23-bittensor-manual-claim-native-staking.md),

- [ ] **AC-13** — **The *All accounts* half is not provable from this diff.** #5093 says
  notifications "show up for each account but not under **All accounts**". AC-6 unfreezes the
  screen's account, which fixes *switching to* All accounts on that screen; whether the
  notifications are also **written** for the All-accounts view is a different question the diff does
  not answer. Verify by hand before ticking #5093's box.

## Localization — 5 of 6 new strings ship as English in every non-English locale

Six keys were added to all five locales, which is the right count. But only
`multisigTxStatusUnavailable` is actually translated in `vi`, `ja`, `ru` and `zh`; the other five —
including both status titles and both explanatory bodies, the entire user-facing point of this
change — are **verbatim English** in all four.

| Key | vi / ja / ru / zh |
| --- | --- |
| `enableNetworkToViewMultisigTx` | English |
| `multisigTxApprovedTitle` | English |
| `multisigTxApprovedContent` | English |
| `multisigTxNoLongerPendingTitle` | English |
| `multisigTxNoLongerPendingContent` | English |
| `multisigTxStatusUnavailable` | **translated** |

This is [US-12.23](US-12.23-bittensor-manual-claim-native-staking.md)'s finding again — *four of
five locales carry the English threshold message* — but sharper: one string in the same batch **was**
translated, so this is a partial pass rather than a missing one, and a locale diff that only counts
keys will not catch it.
