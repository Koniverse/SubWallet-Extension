## Goal

XCM build, fee, dry-run, dry-run-preview and transferable-amount keep working when `/v1` is
retired.

## Background

### Two different "ParaSpell versions" — do not conflate them

[US-13.14](US-13.14-xcm-fee-dry-run-and-validation.md) already carries three ParaSpell rows, and
they are not all the same axis:

| Issue | Shipped | What actually moved |
| --- | --- | --- |
| [#4606](https://github.com/Koniverse/SubWallet-Extension/issues/4606) | 1.3.55 | **SDK** — ParaSpell V4 |
| [#4908](https://github.com/Koniverse/SubWallet-Extension/issues/4908) | 1.3.72 | **SDK** — ParaSpell V5 |
| [#4979](https://github.com/Koniverse/SubWallet-Extension/issues/4979) | 1.3.79 | **HTTP API** — the hosted endpoint path, `/v1` |
| [#5051](https://github.com/Koniverse/SubWallet-Extension/issues/5051) | — | **HTTP API** — `/v1` → `/v2`. *This story.* |

The SDK is a package version in `package.json`; the HTTP API is a path prefix on the hosted
service SubWallet proxies to. #5051 is the direct successor of **#4979**, not of #4908.

### What the wallet calls

`packages/extension-base/src/services/balance-service/transfer/xcm/utils.ts` holds one
`const version` that prefixes all six ParaSpell endpoints — `x-transfer`, `xcm-fee`, `dry-run`,
`dry-run-preview`, `transferable-amount`, `min-transferable-amount`. Every call goes out through
`ProxyServiceRoute.PARASPELL`, so the provider key stays server-side (NFR-16, AD-19) and the
version prefix is the *only* client-side coupling to the provider's API surface.

That is why the change is one line — and why it is not small. Those six endpoints back XCM
transfer construction, fee estimation and the dry-run preview that
[US-11.8](US-11.8-cross-chain-swap-routing.md) uses to validate swap-bridge steps. A silent
response-shape change between `/v1` and `/v2` surfaces as a broken XCM quote, not as a build error.

## Acceptance criteria

- [ ] **AC-1** — **Given** the XCM transfer path, **When** it calls ParaSpell, **Then** every one
  of the six endpoints is requested under `/v2`. *(A single `const version` prefixes all six.
  **True on `koni/dev/issue-5051`, false on `dev`** — the branch is unmerged, so the shipped code
  still calls `/v1`.)*
- [ ] **AC-2** — **Given** `/v2`, **When** an XCM transfer is built and submitted on a live route,
  **Then** it succeeds and the destination receives the tokens. *(Not verified here — this is the
  In-Testing gate on the PR.)*
- [ ] **AC-3** — **Given** `/v2`, **When** `xcm-fee`, `transferable-amount` and
  `min-transferable-amount` are queried, **Then** each returns a usable figure and no route
  regresses to *unavailable* (NFR-22).
- [ ] **AC-4** — **Given** `/v2`, **When** the swap-bridge dry-run preview runs
  ([US-11.8](US-11.8-cross-chain-swap-routing.md) AC path, #4671), **Then** validation still
  rejects the cases it rejected under `/v1`.
- [ ] **AC-5** — **Given** a `/v2` error response, **When** it is handled, **Then** the
  `ParaSpellError` shape (`message`, `error`, `statusCode`) still parses — or the parser is
  updated with it.

> **Nothing is ticked, deliberately.** A ticked AC is a claim about *this* tree
> ([D107](../../CONTEXT.md), [LESSONS §68](../../LESSONS.md)) — and on `dev` the prefix is still
> `/v1`, because PR #5053 is unmerged. AC-1 becomes tickable the moment it merges; AC-2…AC-5 are
> claims about a running network that nothing in this repository can settle, and stay open until
> the PR clears testing.
