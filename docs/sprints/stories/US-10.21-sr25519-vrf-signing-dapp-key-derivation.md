## What the PR does

**A new dApp message, `pub(vrf.sign)`.** `InjectedSigner.signVrf(payload)` is an optional
SubWallet extension to the injected-web3 signer — dApps feature-detect it, and other injected
signers legitimately do not have it. The payload is `{ address, data, context? }`.

**The output is bound to the site's origin, and the wallet supplies the origin.** The signing
context is `"substrate-vrf" || u32_le(len(origin)) || origin || u32_le(len(context)) || context`,
where `origin` is `scheme://host` **taken from the tab, never from the payload**. The length prefix
is what makes the pair injective — without it a caller could craft a `context` that reconstructs
another origin's frame. `http` and `https` derive different keys on the same host, and non-HTTP(S)
origins are refused. The layout is frozen in the code as a deliberate compatibility boundary:
outputs are deterministic per effective context, so changing it rotates every key already derived,
and a revision has to be a new namespace rather than an edit.

**sr25519 only, checked twice** — once in `Tabs.ts` before the request is raised, once in
`RequestVrfSign.sign`. The second is the load-bearing one: the comment records that the non-sr25519
branch of `vrfSign` fakes a VRF by hashing a plain signature, which is exactly the *signature as key
material* pattern this feature exists to replace.

**Bounded input** — data ≤ 64 KiB, context ≤ 1 KiB, both 0x-hex, so the wallet never hashes
unbounded dApp-supplied bytes.

**The result is 96 bytes, `output(32) || proof(64)`, and only the first 32 are deterministic.** The
proof is randomized, so the same request returns a different 96-byte value each time. Both the
`signVrf` contract and `Signer.signVrf` say to derive from the first 32 bytes alone.

**A new confirmation screen** — *Key derivation request*, showing the requesting domain, the account,
a **permanent-key warning** (*"cannot be changed or revoked later … unique to {domain}"*), and a
details modal with **Bound to** and **Context**. Eight new strings; `en` is filled and `ja`, `ru`,
`vi`, `zh` are **empty**.

**Eight tests** — seven in `RequestVrfSign.spec.ts` (origin-bound context, dApp context exposed,
scheme binding, non-HTTP(S) rejected, oversized data and context rejected, non-hex rejected,
non-sr25519 rejected) and one added for `RequestBytesSign` alongside.

## Why EPIC-10 owns it — settled

[EPIC-10](../epics/EPIC-10.md) is the epic that lets a dApp *"approve connections, **signatures** and
transactions"*. The PR confirms the placement: the surface is the injected signer, the origin comes
from the tab, and the whole feature terminates in a dApp confirmation screen. The EPIC-2 and
[US-3.7](US-3.7-account-derivation-custom-path-child-accounts.md) alternatives are ruled out — there
is no new derivation path and no keyring change; it signs with an existing account's sr25519 key.

## The open questions, answered by the diff

1. **Who asks?** The dApp requests a VRF signature over its own payload; the *derivation* is what the
   dApp does with the result. The wallet does not create or store a key.
2. **What does the user approve?** The new confirmation screen, which names the domain and the
   account and warns the key is permanent. It satisfies the
   [US-5.15](US-5.15-signing-prompt-mode-confusion.md) rule — `Bound to` and `Context` show the
   effective context, and `origin` cannot be spoofed through the payload.
3. **Which key?** An existing local sr25519 account. Per-origin uniqueness comes from the context,
   not from a derived keypair.
4. **Priority.** Still open — no label, no assignee, no milestone on either the issue or the PR.
   `P3` remains a placeholder.

      yields a different `output(32)` (`RequestVrfSign.spec.ts:58`, *binds to the scheme, not just
      the host*)
- [x] AC-4: A non-sr25519 account is refused, and the refusal names the reason
      (`RequestVrfSign.ts:73` — *"VRF signing requires an sr25519 account"*; spec *rejects
      non-sr25519 accounts*)
- [x] AC-5: A non-HTTP(S) origin, non-hex input, data over 64 KiB or context over 1 KiB are refused
      (spec: *rejects a non-HTTP(S) origin*, *rejects oversized data and context*, *rejects non-hex
      input*)
- [x] AC-6: The confirmation screen shows the **origin** — scheme and host, `new URL(url).origin`,
      the same value the key is bound to — not a stripped domain; plus the account, the
      permanent-key warning, and `Bound to` / `Context` in the details modal
      (`VrfSignConfirmation.tsx`, after `67939c4315`). *Corrected 2026-09-16: the first draft said
      "domain", and that was the bug review finding 1 caught.*
- [x] AC-7: `signVrf` is optional on `InjectedSigner` and documented as feature-detect
      (`extension-inject/src/types.ts:114–129`); a dApp that does not call it is unaffected
- [x] AC-9: The header of a VRF request reads *Key derivation request*, not *Signature request*
      (`Confirmations/index.tsx` `headerTitle`; key `ui.DAPP.Confirmations.Message.Vrf.keyDerivationRequest`)
- [x] AC-10: `pri(signing.approve.signature)` **throws** for a queued VRF request — the QR, Ledger
      and injected flows cannot complete one with a 64-byte plain signature
      (`Extension.ts` `signingApproveSignature`, `assert(!queued.request.isVrf, …)`). **No unit test
      exercises this** — the reviewer asked for one and it was not written before the merge.
