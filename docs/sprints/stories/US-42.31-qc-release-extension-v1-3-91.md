## Goal

QC the v1.3.91 release end to end, across every build stage from dev merge to production, checking both the release content and that nothing else broke (regression).

## Background

Release content for v1.3.91, from the release note posted 2026-10-09 in product-release.

| Item | Issue | PR | Dev story | QC story |
| --- | --- | --- | --- | --- |
| Improve multisig notification | [#5093](https://github.com/Koniverse/SubWallet-Extension/issues/5093) | [#5095](https://github.com/Koniverse/SubWallet-Extension/pull/5095) | [US-18.5](US-18.5-multisig-notification-improvement.md) | [US-42.29](US-42.29-qc-issue-5093-multisig-notifications.md) |
| Update chainlist stable — maintenance of chainlist | [ChainList #710](https://github.com/Koniverse/SubWallet-ChainList/issues/710) | [ChainList #713](https://github.com/Koniverse/SubWallet-ChainList/pull/713), Extension [#5096](https://github.com/Koniverse/SubWallet-Extension/pull/5096) | — | [US-42.28](US-42.28-qc-chainlist-710-maintenance.md), [US-42.30](US-42.30-qc-chainlist-710-final-recheck.md) |

Both items already have their own QC stories and all of them passed. This story is the release gate — it re-verifies that the same content lands correctly as it moves through each build stage, plus a regression pass at each stage.

Three things shape this run.

None of the three PRs had merged when this story was written on 2026-10-12: #5095, #5096 and ChainList #713 were all still open. The gate cannot start until they are in, so TASK-42.31.2 below checks that first and records the merge commits in the table above.

The chainlist half has been QC'd twice and both results are tied to a particular build. US-42.28 closed 2026-10-07 at 306 lines against beta.4. US-42.30 closed 2026-10-09 at 33 lines against beta.5, covering what changed after US-42.28, and also walked the full 72-chain provider change list on a dev build. Neither of those is a release build. Chain-list is delivered online, so the version the release ships with is whatever is published at that moment, which is the thing this gate has to confirm.

AC-18 of US-42.29 was skipped — the locale pass on the five new multisig notification strings. Reading the diff of PR #5095 suggests they ship as English in vi, ja, ru and zh, with only the sixth string of the batch translated. AC-13 below picks it up, because a release gate is the last point where it can be caught.

## Stages

1. Dev merge — both items merged into the extension, then regression test on the dev environment.
2. Master build — build from master with the release content above, then regression test on an environment closest to production.
3. Draft release — test the draft release build with the release content above, then regression test on a production-like build in draft form.
4. Production — after publishing, a quick recheck on the live production build.

## Regression checklist (main functions)

The dev pass is AC-2-01 to AC-2-31 above, one tickable line each. The same 31 lines are the list for the master build (AC-4) and the draft build (AC-6), and a reduced set for the production recheck (AC-7 group). They are not repeated here per stage — the stage's report records which of the 31 ran and what each gave, and the stage AC above is ticked when the pass finishes.

Depth per stage:

- Dev (AC-2) — the full 31 lines. This is the pass that has to find anything the release content broke, so nothing is skipped.
- Master build (AC-4) — the full 31 lines again, on the build closest to production.
- Draft release (AC-6) — the full 31 lines, plus the fresh install and upgrade runs (AC-10, AC-11, AC-14, AC-15) and the locale read (AC-13).
- Production (AC-7a, AC-7b, AC-7c) — a reduced recheck: unlock, balances, one send, one swap, the multisig notification, Manage networks. Not the full list; the build is already the one tested at draft.

The upgrade path — install v1.3.90, add data, upgrade to v1.3.91, confirm data, settings and the master password are preserved — is AC-11, run at the draft stage, not once per stage.

## Test notes

Written 2026-10-12 from the release note posted on 10-09. Started 2026-10-30 on the subwallet-dev build.

The multisig half passes on the dev build, all 23 lines, run on testnet. A pending approval raises a notification that stays put through an idle minute, through account changes and through chain changes, and it does not blink out and come back with a new timestamp. It survives a failing RPC and comes back right when the RPC does. It reads approved once the current signer signs and no longer pending once the transaction leaves the chain, keeping the account prefix, and each state opens the right thing when clicked — History while pending, a status modal once it is not, the enable-network offer on a disabled chain, a warning toast when the status cannot be read. Other notification kinds, marking read, the filter tabs and signing from a notification are all unaffected.

AC-1a was a single line when this story was written — multisig notification works correctly on dev — which is not something a tester can tick a piece at a time. It is now 23 lines, AC-1a-01 to AC-1a-23, taken from the AC that US-42.29 already proved the feature against, so a session can tick what it actually got through.

It was also silent about which network, so the live-network re-check became AC-1c, and that passes too. It ran against a real multisig on Polkadot Asset Hub with a pending approval the tester did not create — `15RMoJNoFRCWUyeLVrMgwWB23f7bNmk6psC7acBZ4hqmYh1A`, two signatories, one approval in, opened at block 22,309,954. The two are different checks: on testnet the tester makes the multisig and the pending call, so the notification is driven by data the test itself made, while on a live network it comes from elsewhere, which is the case a real user meets.

AC-1b had the same problem and is now 30 lines. It read "the chainlist maintenance is live" — one tick for a change that spans 12 new mainnet chains, 12 testnets, 66 deactivations, 102 Bittensor subnets, 72 chains with rewritten RPC lists and five feature updates. The lines come from the sections of ChainList #710 itself: AC-1b-01 to AC-1b-15 for the chains added, -16 to -18 for the deactivations, -19 to -22 for the subnets, -23 to -28 for the feature updates, and -29, -30 for the RPC changes.

Not every item needs its own line. The 66 deactivated chains are three lines rather than 66, because US-42.28 and US-42.30 already walked them one by one and what matters here is that the release build still behaves. The 72 RPC chains are one line pointing at the list in the 10-09 report for the same reason. The new chains get a line each because nothing has checked them yet.

The chainlist half passes on 2026-11-02, all 32 lines, on both a fresh install and an upgrade from v1.3.90. The 12 new mainnet chains and their 12 testnets are in Manage networks and connect, with the right chainId and native token on each, their own logos and a price where the chain carries a priceId. The deactivated chains are out of the lists while a balance held on them is still readable. The Bittensor subnets carry their new names, symbols and icons with balances unmoved, keyed by netuid. Bittensor and Bittensor Testnet now accept a multisig account and raise a notification on a pending approval. GEB reads GEB on both endpoints with its balance and explorer intact, and Atleta Olympia connects on its new genesis hash.

The regression pass had the same shape of problem as AC-1a and AC-1b, in a different form. AC-2 was one line — regression pass on dev finds no new issues — pointing at a 17-line checklist written to be re-run at all four stages. So the checklist could not be ticked for dev without claiming it for master and draft too, and AC-2 itself only moved when the whole pass was over. A day of regression testing left nothing to record.

It is now AC-2-01 to AC-2-31, each a line a tester can tick when that one is through: accounts and unlocking (01-11), sending and receiving (12-16), swap, stake and claim (17-21), XCM (22-23), dApp and notifications (24-27), networks and settings (28-31). AC-2 stays as the one line that says the dev pass is finished, and is ticked last.

The 31 lines are the list for the master build (AC-4) and the draft build (AC-6) as well — the same lines, run again on that build, recorded in that day's report rather than copied into the story four times. Production is deliberately shallower: AC-7c is unlock, balances, one send, one swap, the multisig notification and Manage networks, because the build published is the one already tested at draft. The upgrade path moved out of the per-stage list to AC-11, where it belongs — it is run once, at draft.

The line about XCM is worth naming. The old checklist had relay to parachain and parachain to parachain as two items with no fee or balance check on one of them; both now say the fee shows and both sides update, which is where XCM breaks when it breaks.

The dev regression pass itself passes on 11-02, all 31 lines. Four checks that were not on the old 17-line list pass on their first run: a wrong master password refused without a lockout, a custom network and token surviving a reopen, the settings that have to persist, and the earning screen loading its positions and APY. Both XCM lines pass on the stricter wording. Nothing in the release content broke anything on the list.

105 AC in total, 88 pass. Dev is finished — the release content and the regression pass both. The 17 left are every stage past dev: the master build, the draft release, production, the locale read and the fresh-install and upgrade runs.
