## Goal

QC the v1.3.90 release end to end, across every build stage from dev merge to production, checking both the release content and that nothing else broke (regression).

## Background

Release content for v1.3.90, from the release note posted 2026-09-17. Both PRs merged that morning, minutes apart.

| Item | Issue | PR | Merge commit | Dev story | QC story |
| --- | --- | --- | --- | --- | --- |
| sr25519 VRF signing for dApp key derivation | [#5072](https://github.com/Koniverse/SubWallet-Extension/issues/5072) | [#5076](https://github.com/Koniverse/SubWallet-Extension/pull/5076) | `a4799cfbb1` | [US-10.21](US-10.21-sr25519-vrf-signing-dapp-key-derivation.md) | [US-42.25](US-42.25-qc-issue-5072-sr25519-vrf-signing.md) |
| Manual claim for Bittensor native staking | [#5064](https://github.com/Koniverse/SubWallet-Extension/issues/5064) | [#5065](https://github.com/Koniverse/SubWallet-Extension/pull/5065) | `1b7abee917` | [US-12.23](US-12.23-bittensor-manual-claim-native-staking.md) | [US-42.23](US-42.23-qc-issue-5064-bittensor-manual-claim.md) |

Each item already has its own QC story covering the feature-level checks, and both passed. This story is the release gate — it re-verifies that the same content lands correctly as it moves through each build stage, plus a regression pass at each stage.

Two things shape this run.

The Bittensor manual claim was QC'd in [US-42.23](US-42.23-qc-issue-5064-bittensor-manual-claim.md) on 2026-08-26, then dropped from v1.3.89 and left waiting for a release to pick it up. That was three weeks ago against a build nobody has rebuilt since. The result does not carry over on age alone; this gate re-runs it.

The VRF signing QC in [US-42.25](US-42.25-qc-issue-5072-sr25519-vrf-signing.md) ran on 2026-09-17 against an unmerged PR build and passed 11 of 11, but three groups of checks were left out of its scope and nobody has run them: the two-origin comparison that the feature exists for, the five locales on the confirmation screen, and the refusal cases. AC-13 and AC-14 below pick up the first of those, because a release gate is the last point where it can be caught.

## Stages

1. Dev merge — both issues merged into the extension, then regression test on the dev environment.
2. Master build — build from master with the release content above, then regression test on an environment closest to production.
3. Draft release — test the draft release build with the release content above, then regression test on a production-like build in draft form.
4. Production — after publishing, a quick recheck on the live production build.

## Regression checklist (main functions)

Run this list at each stage (dev, master, draft, production quick recheck at reduced depth). Tick a line only when it has passed at every stage — the stage-level result lives in AC-2, AC-4, AC-6 and AC-7. Ran and passed on dev on 2026-09-17.

- [ ] Create a new account / import an existing account (mnemonic, private key)
- [ ] Switch between accounts, view balances across chains
- [ ] Unlock with the master password, and unlock with the passkey if it is on
- [ ] Auto-lock triggers on time and the wallet reopens correctly
- [ ] Send a native token, confirm it goes through with correct fee display
- [ ] Receive a token (show/copy address, QR)
- [ ] Swap tokens (at least one route)
- [ ] Stake and unstake on at least one network
- [ ] Claim rewards on Bittensor native staking, the release item, and on one other network to show the shared path still works
- [ ] XCM transfer relay chain → parachain
- [ ] XCM transfer parachain → parachain, with correct fee and balance update on both sides
- [ ] Connect to a dApp (WalletConnect or injected), sign a message and a transaction
- [ ] A dApp asks for a derived key, the confirmation screen appears and approving returns a signature
- [ ] Export account (JSON / seed phrase) and remove account
- [ ] App upgrade path: install v1.3.89, add data, upgrade to v1.3.90, confirm data, settings and the master password are preserved
