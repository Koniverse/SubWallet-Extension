New chain reads: `betaBasketRuntimeApi.getRootBasketOwed(address)` and `getRootBasketPositions(address)`,
plus `subtensorModule.rootClaimableThreshold` behind `getRootClaimThreshold()`.

### The questions, answered

1. **What is not automatic?** Root (netuid 0) basket rewards require a user-triggered claim. The PR
   turns `claimReward` on for the root handler and explicitly **off** for the subnet handler.
2. **Which reward type?** Root-network TAO — *not* subnet/alpha emissions. **This resolves the
   overlap worry with [US-12.6](US-12.6-bittensor-dtao-subnet-staking.md)**: there is none, and the
   `dtao.ts` edit exists precisely to say alpha positions have nothing to claim.
3. **Priority.** Raised P3 → **P2**: this is a claim path for rewards users currently cannot collect,
   not a convenience.

### Question 4 is *not* answered — and it is the one that matters

v1.3.86 **removed** a deprecated Bittensor root claim type (#5045,
[US-12.21](US-12.21-earning-fixes-recovered-from-uncategorized.md)). This PR adds a root claim path
built on a **different** runtime API (`betaBasketRuntimeApi`), so on the evidence it is a
replacement rather than a revival — but **nothing in the PR or the issue says so**, and the
relationship between the removed type and this one is exactly what a reviewer should confirm.

### The risk this story flagged was checked, and the scale holds

AC-3 called out `RootClaimableThreshold` as a substrate-fixed `I96F32` needing a `2^32` divide, and
warned that a wrong scale would show *a plausible number rather than failing loudly*. US-42.23 AC-10
tested it end-to-end: `{ bits: 2147483648000000 }` reads back as **500,000 rao (0.0005 TAO)**, so the
division holds in the running build and not only in the diff. The `500000` fallback behaves when the
query is absent (AC-4).

The dust case behaves too: with rewards pending but every validator below the threshold, the claim is
**refused before submission** — no extrinsic, **no fee charged**. That was the failure mode worth
having: a no-op that still costs the user a fee.

### What is now the problem

**The only verification this feature has is one manual pass on an unmerged branch**, and the release
that would have re-verified it on a real build no longer includes it. US-42.23 says so itself. It
still ships **no test**, so if the PR sits and the branch drifts, the 16/16 decays into a claim about
a commit nobody is building any more.

## Acceptance criteria

Derived from the **code**, not from the issue — refutable against the branch:

- [x] **AC-1** — Root (netuid 0) positions expose a claim action; subnet/alpha positions do not
  (`claimReward: true` in `tao.ts:270`, `false` in `dtao.ts:95`).
- [x] **AC-2** — Owed rewards come from `betaBasketRuntimeApi.getRootBasketOwed()` and match what
  the chain reports; the position list comes from `getRootBasketPositions()` (`tao.ts:597`).
- [x] **AC-3** — `RootClaimableThreshold` is decoded as a substrate-fixed `I96F32` — the raw bits
  carry **32 fractional bits**, so the value is divided by `FIXED_POINT_32_DIVISOR = 2^32` and
  floored (`tao.ts:630`). An unscaled read is wrong by nine orders of magnitude.
- [x] **AC-4** — When `subtensorModule.rootClaimableThreshold` is absent, unreadable, or negative,
  the handler returns `UNKNOWN_ROOT_CLAIM_THRESHOLD = 0` — **filter nothing and let the chain
  decide** — rather than throwing (`tao.ts:614–636`). A chain reporting `0` is honoured as `0`.
  *Corrected 2026-09-17: the first draft said the fallback was `DEFAULT_ROOT_CLAIM_THRESHOLD`
  (`500000` rao); that was `f66902bab9`'s behaviour and `0071a73f79` replaced it before merge.
  The shipped fallback is 0, which means an unreadable threshold produces a claim the chain may
  settle as a fee-charging no-op — the exact case AC-5's guard exists for, and one it cannot see.*
- [x] **AC-5** — When positions exist but none clears the threshold, the claim is refused with
  `rewardBelowClaimThreshold` naming the threshold and symbol (`tao.ts:706`), rather than building a
  transaction that settles nothing and still charges a fee.
- [x] **AC-6** — `bg.EARNING.services.service.earning.nativeStaking.tao.rewardBelowClaimThreshold`
  is present in all 5 locale files and is what the user sees. **Four of the five carry the English
  text** — `ja`, `ru`, `vi`, `zh` are untranslated. The AC as written holds; the translation does not.
- [x] **AC-7** — The path removed in v1.3.86 (#5045) is not reintroduced — no `rootClaimType` /
  `RootClaimType` symbol survives in `extension-base`; this is a distinct runtime API.
