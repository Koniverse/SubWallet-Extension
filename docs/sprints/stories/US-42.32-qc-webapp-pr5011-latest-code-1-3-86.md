## Goal

QC the Web App after [PR #5011](https://github.com/Koniverse/SubWallet-Extension/pull/5011) brought the Extension's 1.3.86 code into it and added the Extension-only features the Web App was missing ([Issue #5004](https://github.com/Koniverse/SubWallet-Extension/issues/5004)).

Two things have to be checked, and they are different in kind. The ten features are checked because they have never run on the Web App. Everything else is checked because 932 files changed underneath it.

The scope is not in the body — it is in the developer's comment of 2026-06-26, which lists twelve items, ten of them with their own issue. The issue is still open; the PR that did the work is merged.

[PR #5011](https://github.com/Koniverse/SubWallet-Extension/pull/5011), `koni/dev/issue-5004` into `webapp-dev`, merged 2026-08-07 as `b554a002c6`. 932 files, +65,206 / −25,477, 1,634 commits, and an empty body.

## Test notes

Written 2026-11-03 from the diff of PR #5011 and the developer's scope comment on [Issue #5004](https://github.com/Koniverse/SubWallet-Extension/issues/5004). The AC describe what the commits actually do; none is inferred from the issue title.

The first draft missed four features, and the reason is worth keeping. The issue body is one sentence, so the draft was built by grepping the merge for commits titled `[Issue-#5004]` — nine of them — and writing AC from those. But the scope is in a comment, not the body: the developer listed twelve items on 2026-06-26, ten with their own issue number. Four of those ten were done under their own issue number and so carry their own commit titles, which the grep never saw: locked balance (#4708, `0a828ce5c4`), Bittensor staked swap balance (#4899, `5bc62fdc2c`), XCM destination fee (#4278, `36c7c1305a`) and NFT without `tokenOfOwnerByIndex` (#4568, `3973b29199`). All four are in the merge and all four are now AC-11 to AC-14.

The lesson is the same shape as LESSONS §69: an empty-looking issue is a claim, not a fact. Read the comments before concluding the scope has to be reconstructed from commits, and when reconstructing anyway, do not assume the issue's own number is in every relevant commit title.

The scope is awkward on purpose. The PR is 932 files and 1,634 commits, but only the work named in the comment is this issue's own — the rest is the Extension's history arriving at the Web App in one merge, and it reaches v1.3.86. Writing an AC for each of the 1,634 would be false precision; writing one AC for the whole merge would be the mistake [US-42.31](US-42.31-qc-release-extension-v1-3-91.md) had to correct three times. So the ten features get 108 lines between them, and the merge gets a regression pass with its case list in the report.

The first draft of these AC was reviewed against the diff a second time and six lines were wrong. They are listed here because the same mistakes are easy to repeat on the next story written from a diff.

The turn-off-all switch reads the opposite way round from what the first draft assumed. `checked={!hasActiveChains}` and `disabled={!hasActiveChains}`: with networks on, the switch is off and pressable; once everything is off, it shows as on and greys out. The draft had it off when nothing was enabled, which is backwards and would have been logged as a bug on a working build.

Trust Wallet import has a step the draft skipped — the option opens an account type modal first and only then the seed screen, with `?type=` in the URL. It also restricts the word count to 12 where the normal import offers 12, 15 and 24, and a general phrase pasted into it warns rather than refuses. Back from it returns to the Trust Wallet modal, not the general one.

The alpha transfer filter is `activeStake > 0`, not "holds a position". A validator with a position but nothing active is not in the list, which is a different test.

The worst one: the draft had an AC saying a transfer to the same validator as the source is refused. Nothing in the commit does that — `validateAlphaAmount` checks the amount only, and there is no comparison between the two validators anywhere in the diff. That AC asserted behaviour that does not exist, which is exactly what writing from the issue text instead of the code produces. It is now AC-6-15, worded as something to observe and raise, not something to confirm.

Same correction on nested NFT. The draft said sending a nested NFT either carries the children or is refused with a reason. The commit adds a Send button and wires it to the existing send-NFT flow; it says nothing about children. AC-5-14 now asks the tester to record what happens rather than to confirm a rule nobody wrote.

Two features are still worth flagging before the run.

The alpha token transfer is the heaviest, and the least like anything already on the Web App. It moves a Bittensor subnet position from one validator to another, so it needs an account that actually holds alpha on at least two validators, with active stake on them; without that the pickers cannot be exercised.

Nested NFT adds two screens that did not exist on the Web App, each with its own route — `bundle-item-detail` and `view-structure`. The structure view and the parent-child navigation are where a merge like this usually breaks, because `router.tsx` changed in the same PR.

The locale work is in the PR twice, which is worth knowing: `1bce06e1d7` rewrote the key format across all five translation files — roughly 700 lines changed per locale — and `156989f6f1` moved the earning terms modal onto it. AC-9 is the check that the rewrite did not leave a screen showing raw keys. That is a cheap sweep and should be done early, because a raw key is visible without any test data.

Points: 21, up from 13. The first estimate covered six features; the real scope is ten, and the four that were missing are not small — the locked balance breakdown has to be checked against an explorer, the staked swap balance needs a Bittensor position that can actually be swapped, and the XCM fee display needs a route that can be run end to end. Six of the ten need chain state or a specific contract set up before anything can be tested.

The AC count went 75 → 86 → 112 across two reviews. Only the last increase moved the points, because the first was the same work described more finely and the second was work that had been left out.
