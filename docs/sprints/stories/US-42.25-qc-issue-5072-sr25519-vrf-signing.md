The dev-side story is [US-10.21](US-10.21-sr25519-vrf-signing-dapp-key-derivation.md), written from the same PR diff. Its AC are the code-level claims; the AC here are the user-level checks.

### What the feature does, in plain terms

A dApp asks the wallet to sign a piece of data with a special kind of signature called VRF. The dApp then uses the result to make itself a key of its own. The wallet does not create or store that key — it only signs.

The important part for testing is what the signature is tied to. The wallet mixes the **site's origin** into the signature, and it takes that origin from the browser tab, never from what the dApp sends. So:

- Two different sites asking for the same data get different results.
- `http://app.com` and `https://app.com` count as different sites and get different results.
- `https://app.com` and `https://www.app.com` also count as different and get different results.

That is the whole security point: one site can never work out another site's key.

The result is 96 bytes long. Only the **first 32 bytes are stable** — ask twice with the same data from the same site and the first 32 bytes match, but the remaining 64 change every time. That is by design, and it is worth knowing before testing so a changing value is not written up as a bug.

### Why the confirmation screen matters

There is a new screen called **Key derivation request**. It names the site, names the account, and warns that the key is permanent — it cannot be changed or revoked later.

The screen must show the **origin** (scheme and host together, like `https://app.com`), not a trimmed domain. This was a real bug caught in review: the first version showed `app.com`, so a user saw the same sentence for three sites that produce three different keys. Fixed in `67939c4315`, and AC-6 is the check that it stays fixed.

### Limits the code enforces

- sr25519 accounts only. Other account types are refused.
- Data at most 64 KiB, context at most 1 KiB.
- Both must be 0x-hex.
- Non-HTTP(S) origins refused.

## Things to check

A test dApp that calls `signVrf` is needed for most of these. Without one, only AC-13 and AC-14 can be run.

**The happy path**

- [ ] AC-1: A dApp asks for a VRF signature on an sr25519 account, the confirmation screen appears, approving it returns a 96-byte result
- [ ] AC-2: Rejecting the prompt returns an error to the dApp and produces no signature
- [ ] AC-3: Asking twice from the same site with the same data gives the same first 32 bytes; the full 96 bytes differ each time

**Tied to the site — the part that must not break**

- [ ] AC-4: The same request from two different sites gives different first-32-byte results
- [ ] AC-5: `http://` and `https://` on the same host give different results, and so do `app.com` and `www.app.com`

**The confirmation screen**

- [ ] AC-6: The screen shows the full origin — scheme and host, `https://app.com` not `app.com` — so three sites that derive three different keys never read as one
- [ ] AC-7: The header reads **Key derivation request**, not *Signature request*
- [ ] AC-8: The screen names the account being used and shows the permanent-key warning
- [ ] AC-9: The details view shows **Bound to** and **Context**, and the values match what was asked for
- [ ] AC-10: The screen reads correctly in all five languages — en, ja, ru, vi, zh — with no blank strings and no untranslated keys

**What must be refused**

- [ ] AC-11: A non-sr25519 account is refused, and the message says why
- [ ] AC-12: Data over 64 KiB, context over 1 KiB, input that is not 0x-hex, and a non-HTTP(S) origin are each refused with a clear error and no signature

**Nothing else breaks**

- [ ] AC-13: Ordinary dApp signing still works — connect, sign a message, sign a transaction — and a dApp that never calls `signVrf` behaves exactly as before
- [ ] AC-14: The passkey unlock setup modal that rides in this PR behaves: it appears after login, Enable turns passkey unlock on, Not now dismisses it and it does not come back, and the master password still unlocks the wallet either way

**Install paths**

- [ ] AC-15: AC-1 to AC-14 hold on a **fresh install** (no prior version or data)
- [ ] AC-16: AC-1 to AC-14 hold on an **upgrade from the current release** — existing accounts, settings and the master password all still work, and no account is lost
