## Goal

Check that a multisig approval notification stays put until it has something to say, and that when it no longer needs action it says so instead of vanishing.

## What is in this change

[#5093](https://github.com/Koniverse/SubWallet-Extension/issues/5093) — Improve multisig notification, by tunghp2002, on [PR #5095](https://github.com/Koniverse/SubWallet-Extension/pull/5095) (10 files, +233/−46, branch `koni/dev/issue-5093`).

The issue body names three symptoms and five root causes, so the AC below come from a written problem rather than from the diff alone.

What users saw:

- A notification appeared, then disappeared on its own, sometimes coming back later as a new unread one with a new timestamp.
- Notifications showed under each account but not under All accounts.
- Once a notification was gone, there was no way to tell whether the transaction had been approved, executed or cancelled.

What the code did, from the issue:

1. `clearMultisigApprovalNotifications` deleted every notification of a multisig whose transaction was missing from the latest update, so any incomplete update wiped them.
2. `subscribeDataWithMulti` turns an RPC error into an empty result and completes the stream, which looked exactly like "no pending transaction" — so the notifications went and the subscription stopped until the next reload.
3. A pending transaction whose block could not be read was skipped and its notification deleted.
4. Account switch, add and remove, chain enable, disable and update, and a wrapped `transaction.done` each trigger a full resubscribe, giving causes 2 and 3 another chance each time.
5. The notification screen kept the account id it mounted with in `useState`, so switching account on that screen still fetched the old one.

What the fix does: notifications are updated with a status rather than deleted. The status is `APPROVED` when the current signer has approved and the transaction waits on others, and `RESOLVED` when it is off chain — executed or cancelled. An incomplete storage read now throws and resubscribes instead of reporting an empty list, a transaction whose extrinsic cannot be resolved keeps its last known data, and the screen follows the current account instead of freezing it.

## Why this is worth 13

The failure modes are timing and error conditions, not screens. Causes 2 and 3 only show up when an RPC is flaky or a block is pruned, and cause 4 only when a reload lands at the wrong moment. Reproducing those deliberately is most of the work, and a run that never provokes them proves very little.

A multisig with several signatories is needed as well, since the point of the change is what the notification says to a signer who has already approved while others have not.

## Before testing

- A multisig account with at least three signatories, on a chain the wallet supports, with the wallet holding more than one signatory so both sides of a pending approval can be driven.
- A second wallet or device for the other signatories, to approve or cancel from outside.
- A pending multisig transaction that stays pending long enough to work with.
- A way to make the chain's RPC fail or respond slowly — a bad custom provider is enough — for AC-7 and AC-8.
- The ability to switch locale, for AC-18.

## Things to check

The notification stays

- [x] AC-1: A pending multisig transaction raises a notification, and it is still there after a minute of the app sitting idle
- [x] AC-2: The notification does not disappear and reappear with a new timestamp while the transaction stays pending
- [ ] AC-3: The notification shows under the signatory account and under All accounts
- [ ] AC-4: Switching account on the notification screen itself refetches — opening on one account and switching to All accounts shows the right list, not the first account's
- [ ] AC-5: Adding or removing an account leaves the notification in place
- [ ] AC-6: Enabling, disabling or updating a chain leaves notifications of other chains in place

The notification survives a bad read

- [ ] AC-7: With the chain's RPC failing, notifications of that multisig are not cleared — they stay until the RPC answers again
- [ ] AC-8: After the RPC recovers, the notification list is correct again without reloading the extension by hand
- [ ] AC-9: A transaction whose extrinsic cannot be resolved keeps its notification and its last known data rather than vanishing

The notification says what happened

- [ ] AC-10: After the current signer approves, the notification reads "Multisig transaction approved" with the content about waiting for other signatories, instead of disappearing
- [ ] AC-11: After the transaction executes, the notification reads "Transaction no longer pending" with the content saying no further action is needed
- [ ] AC-12: A cancelled transaction reads the same "no longer pending" wording as an executed one. The code has one branch for both — a transaction that is no longer on chain becomes RESOLVED without asking why — so this confirms they are indistinguishable rather than looking for a difference
- [ ] AC-13: The account prefix in square brackets at the start of the title is kept when the title is replaced
- [ ] AC-14: Clicking a notification whose transaction is still pending opens History with that transaction, as before
- [ ] AC-15: Clicking an approved or resolved notification opens a modal naming the status, with an "I understand" button, rather than navigating to a transaction that is not there
- [ ] AC-16: Clicking a notification on a disabled chain offers to enable the network, with the message naming that network, and works on re-click after enabling
- [ ] AC-17: When the status cannot be read — the notification is gone, or the background has no record of the pending transaction — a warning toast says so and the notification is left in the list rather than removed
- [ ] AC-17a: Clicking a pending notification whose transaction the background no longer has shows the same warning and leaves the notification alone — an absent transaction is not proof it was executed, which is why the code checks the cache rather than assuming
- [ ] AC-17b: Clicking the same notification repeatedly while the first check is still running does nothing twice — the second click is ignored until the first finishes

Everything else still works

- [ ] AC-18: The five new strings are checked in each locale the extension ships — en, vi, ja, ru, zh
- [ ] AC-19: Notifications of other kinds — withdraw, claim, bridge, process — are unaffected in content, order and unread state
- [ ] AC-20: Marking read and marking all read still work. Note that a notification turning APPROVED or RESOLVED is marked read by the code itself, so it leaves the unread count on its own — that is intended, not a bug
- [ ] AC-21: The notification filter tabs still sort and filter correctly with the new statuses present
- [ ] AC-22: Signing a multisig transaction from the notification still reaches the signing flow and completes
