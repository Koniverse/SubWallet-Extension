## B. #5055 had a QC page and no owning code story

### The same gap as three days ago

[2026-08-10 §B](2026-08-10.md) found #5042 with two `done` QC stories and no story owning the
code, and closed it with [US-5.15](../sprints/stories/US-5.15-signing-prompt-mode-confusion.md).
**#5055 arrived in exactly the same shape two days later:**
[US-42.14](../sprints/stories/US-42.14-qc-issue-5055-nominator-unstaking-eras-dot-2-days.md) was
written the day the fix merged and records 6/6 AC passing across fresh install and upgrade — and
nothing in EPIC-12 said what had been built.

**A QC page records that something was checked. It does not record what was built.** The two are
different claims and only one of them was in the docs. Left alone, the FR the change defends would
have had a passing test and no implementation record — which is [rule 9](../../AGENTS.md)'s
failure mode arriving from the other direction.

### What the change is

`bondingDuration` is the *slashing-era* window. Where a runtime carries
`staking.nominatorFastUnbondDuration` **and** `staking.areNominatorsSlashable` reads `false`, that
exposure does not apply to nominators and the chain lets them unbond on a shorter clock. Every
relay-chain unstaking figure in the wallet read the long constant, so on Polkadot the wallet quoted
**28 days for a 2-day wait** — wrong in the direction that makes the product look worse than it is.

One helper, `getNominatorUnstakingEras()`, and four call sites:

| Call site | Path |
| --- | --- |
| `NominationPoolHandler` | `earning-service/handlers/nomination-pool/index.ts:112` (FR-115) |
| `RelayNativeStakingPoolHandler` | `earning-service/handlers/native-staking/relay-chain.ts:82` (FR-114) |
| `subscribeRelayChainStakingMetadata` | `koni/api/staking/bonding/relayChain.ts:131` |
| `getRelayChainStakingMetadata` | `koni/api/staking/bonding/relayChain.ts:184` |

The last two are the pre-`EarningService` path, still wired up. Both had to move: the subscription
and the one-shot feed the same screen, and migrating one leaves a view that disagrees with its own
refresh.

### Resolved — [US-12.22](../sprints/stories/US-12.22-nominator-fast-unbond-duration.md)

`done`, `version_shipped: 1.3.87`, `commit: d7e7d847e5`, `prd_ref: [FR-114, FR-115]` as
**defended**, not owned — US-12.1 and US-12.2 keep their single ownership in EPIC-12's FR Coverage
table ([rule 8](../../AGENTS.md)). Not a row on either of them: both shipped years ago and
[rule 9](../../AGENTS.md) says new work is a new story, and the change spans both anyway.

Its six ACs are claims about the code and each carries a command that fails if the claim is false
([LESSONS §68](../LESSONS.md)); all six were run. **The load-bearing one is AC-3** — *exactly one
direct `bondingDuration` read survives in the entire codebase, and it is the fallback inside the
helper*. That is the only AC here that would catch a fifth call site being added later against the
old expression; the other five would all still pass.

### Left standing — nothing tests the branch

The helper has two branches and **no unit test covers either**. Every AC on US-12.22 is a static
claim about source text, so none of them survives someone inverting the `=== 'false'` comparison —
the single most likely way this regresses. The behaviour was verified once, by hand, on one chain
(US-42.14).

A mocked-`api` spec would cost little and the repo already has the shape for it
(`RequestExtrinsicSign.spec.ts`, from US-5.15). **Recommended and not taken** — writing it is new
work and belongs in the sprint that picks it up, not appended to a story that shipped without it.
Recorded in US-12.22 § "Open".
