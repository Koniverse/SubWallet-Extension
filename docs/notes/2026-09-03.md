## B. I was wrong about the chainlist half — for nine days, in four files

The single most important thing in this pass, and it is a correction of my own work.

On 2026-08-25 I wrote that the data half of the #5062 fix **had no issue and no PR** in
`SubWallet-ChainList`, and drew the actionable conclusion that *merging PR #5063 would close the
issue and leave the bad route live in production data.*

**It had already merged.** [ChainList PR #709](https://github.com/Koniverse/SubWallet-ChainList/pull/709)
— `[Issue-5062-extension] Repoint KAH<>PAH XCM refs`, +151 / −8 — landed **2026-08-24**, the day
*before* the claim, carrying exactly the four edits the issue prescribed.

### How

The check was `gh issue list --repo Koniverse/SubWallet-ChainList --search "updated:>=2026-08-20"`.
It returned nothing, and I treated nothing as absence. Two assumptions were buried in one command:

1. that the work would be tracked as an **issue** — it was a pull request;
2. that it would carry a ChainList issue number — it is titled with the **Extension** one.

Either alone hides it. And the conclusion was worse than the gap: it was **specific, actionable and
wrong**, which is the kind that gets repeated. It propagated into US-13.19, sprint-2026-W35,
CLAUDE.md and two sections of the 08-25 note before anyone checked.

### What caught it

[US-42.22](../sprints/stories/US-42.22-qc-issue-5062-repoint-kah-pah-usdt-xcm.md) **AC-9** — written
to force the question *"does this build contain the data fix, the guard, or both?"* against a build
rather than against a search result. An acceptance criterion aimed at a running artefact beat a
tracker query, which is the whole argument for writing ACs that way.

### The lesson, in its third shape this month

[LESSONS §69](../LESSONS.md) says a link an API hands you is a claim, not a fact. In August that was
GitHub's closing-PR field; on 08-25 it was the issue *state* (#5058 closed by hand while unmerged);
now it is **an empty search result**. Same failure, three surfaces.

*"I looked and found nothing"* and *"there is nothing"* are different sentences, and only the first
one is ever earned by a single query. **A negative finding deserves the same corroboration as a
positive one** — and when it spans two repositories, search both, for PRs as well as issues, by title
as well as by number.

Corrected in US-13.19 (with the reasoning kept, not just the fact), sprint-2026-W35, CLAUDE.md, and
[§L of the 08-25 note](2026-08-25.md) — appended as a correction rather than an edit, because a
record that gets edited to stay current stops being a record.

## E. The branch had diverged 11↔11 — and it was not a force-push

Recorded because the shape is alarming and the cause was not.

`git status` opened at **`ahead 11, behind 11`**. That reads like a rewritten history, so nothing was
merged until both sides were listed:

| Side | What it held |
| --- | --- |
| local | the **code** merges — PR #5061, PR #5063, and `Merge branch 'subwallet-dev' into dev` |
| origin | the **docs** commits — QC PRs #5067, #5068, #5069 (US-42.22, US-42.23, US-42.21 updates) |

Complementary, not conflicting: someone merged code into local `dev` without pushing while the QC
docs landed on `origin/dev`. The same 2↔2 split as [2026-08-13 §A](2026-08-13.md), just larger. A
plain merge resolved it with no conflicts.

**The check that mattered took one command** — listing `origin/dev..HEAD` and `HEAD..origin/dev`
separately. `ahead N, behind N` alone cannot distinguish a force-push from two people working in
parallel, and the two have opposite correct responses.

One thing the merge brought in is worth noting: `686c274093 docs: correct #5058 state in US-42.20 —
closed by hand, PR still unmerged` — the team acting on [§J of 08-25](2026-08-25.md). That correction
is now itself outdated, because PR #5061 merged on 08-27. Things move.
