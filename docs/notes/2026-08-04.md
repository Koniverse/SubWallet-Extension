## A. Security recheck — Substrate signing prompt can misrepresent an extrinsic

### Trigger

Polkadot published a postmortem on 2026-07-31: [“Update polkadot{.js} extension to 0.64.0: signing prompts could hide the real transaction”](https://forum.polkadot.network/t/update-polkadot-js-extension-to-0-64-0-signing-prompts-could-hide-the-real-transaction/18291).

The reported defect allowed a site to submit a request through the extrinsic-signing channel while shaping its payload so that the signing prompt rendered it as an inert off-chain message. The signature was over the extrinsic, not the displayed message. The post says upstream polkadot{.js} extension versions before 0.64.0 were affected and that the maintainers are not aware of exploitation.

### Fix as proposed

The change closes the gap at the background layer first, then makes the UI reflect it.

**Background — `packages/extension-base`.**

- `RequestExtrinsicSign` now records `isRawDataInExtrinsic = 'data' in payload` at construction time.
- `RequestExtrinsicSign.sign()` asserts on that flag and throws `Unexpected raw data in an extrinsic signing payload`. This is the load-bearing part: a payload with raw `data` arriving on `pub(extrinsic.sign)` can no longer produce a signature, regardless of what any UI does.
- `RequestSign` gains `readonly isRawDataInExtrinsic?: boolean`, so the discriminant the background always had now reaches the signing-request subscription.
- New `SubstratePayloadErrorType` enum: `Decode` and `RawDataInExtrinsic`.
- New test `RequestExtrinsicSign.spec.ts` — asserts the flag is set for a raw-`data` payload and that `sign()` throws.

**UI.**

- `useParseSubstrateRequestPayload` returns `payloadError` as `{ type, message? }` instead of a bare string, and short-circuits on `isRawDataInExtrinsic` before any parsing.
- `Sign/Substrate.tsx` — `isMessage` becomes `!payloadError && isSubstrateMessage(payload)`, so the request stops being classified as a message; an error `AlertBox` is shown; Approve is disabled; the QR display modal and signature scanner are not rendered.
- `variants/Message/SignConfirmation.tsx` (web-ui) — hides *View details* and the detail modal when `payloadError` is set.
- New key `ui.DAPP.Confirmations.Sign.Substrate.dappSentRawDataInExtrinsicRequest`: *“This dApp sent a raw message through a transaction-signing request. No signature can be created. Reject this request and contact the dApp.”* English filled; `ja`, `ru`, `vi`, `zh` added as empty placeholders in both the `extension-koni` and `webapp` locale sets.

### Why the two pull requests differ in size

The base branches are not at the same point. `subwallet-dev` already carries the `payloadError` plumbing in `extension-koni-ui` (used for decode failures), so #5043 only has to add the new error type and wire `isRawDataInExtrinsic` through it — 10 files. `webapp-dev` has no `payloadError` handling in either `extension-koni-ui` or `extension-web-ui`, so #5044 backports that plumbing as well as adding the fix — 18 files. The two are the same fix, not two different designs.

### Assessment for SubWallet Mobile

Status: **base-level fix now fails closed; the mobile UI path is still unverified and unfixed.**

The installed `@subwallet/extension-base` version is `1.3.83-0`, which predates this change. The original reasoning stands for that version:

1. The background router chooses the signing behaviour from the incoming channel:
   - `pub(bytes.sign)` creates `RequestBytesSign`.
   - `pub(extrinsic.sign)` creates `RequestExtrinsicSign`.
2. `RequestSign` exposes only `payload` plus `sign(...)`; it has no channel/discriminant when it reaches the signing-request subscription consumed by the mobile UI.
3. Mobile classifies a request as raw/message with `isRawPayload`, which returns true whenever `payload.data` is truthy.
4. That payload-derived classification controls both the confirmation content and the signing UI. A request classified as raw is rendered as a message rather than an extrinsic with decoded call data.

Relevant mobile call sites:

- `src/utils/confirmation/request/substrate.ts`
- `src/screens/Confirmations/index.tsx`
- `src/screens/Confirmations/variants/SignConfirmation/index.tsx`
- `src/screens/Confirmations/parts/Sign/Substrate.tsx`
- `src/hooks/transaction/confirmation/useParseSubstrateRequestPayload.ts`

Once mobile consumes an `extension-base` build containing #5043, the `sign()` assert prevents the signature on its own. It does not fix the display: mobile would still render the message-signing confirmation, and the failure would surface only after the user approves. The UI-side gating in this fix lives in `extension-koni-ui` and `extension-web-ui`, neither of which mobile uses — mobile needs the equivalent change in its own screens, and an `extension-base` release to depend on.

### Remaining verification

- Reproduce with a controlled dApp sending an extrinsic-channel payload that includes `data`, on the fix branches, and confirm the prompt shows the new error and cannot be approved.
- Confirm no legitimate request carries a `data` field on `pub(extrinsic.sign)` — `'data' in payload` is a presence check, so an empty-string `data` also trips it.
- Test external browser dApp requests, WalletConnect requests, and internal transaction requests separately.
- Test password, QR, Ledger, and other hardware-account signing paths, since they share parts of the same payload parsing/rendering flow.
- Verify Android and iOS behaviour independently, against a build that includes the `extension-base` change.
- Review every remaining use of `isRawPayload` and any other payload-shape-based message/transaction classification, in mobile and in the two UI packages.
- Fill the `ja`, `ru`, `vi`, `zh` translations before release; they currently ship empty.
- Confirm whether the current `Unknown signed extensions` console warning is only a decoding/metadata compatibility warning or changes any confirmation data shown to the user. It is not evidence by itself of this issue.

### Deliberately not covered

No release decision, version-bump plan, or user communication is included. Those should follow the review of #5043 and #5044 and the mobile-side work above.

## B. Batch import of ~30 accounts spins on the unified-account migration

**The durable record is [LESSONS §71](../LESSONS.md#71-import-runs-the-unified-account-migration-inline-and-its-cost-is-per-keypair--interrupting-it-leaves-accounts-that-cannot-sign).**
This section is the dated entry point. **No tracker issue exists**, so §71 is the only record.

Batch-importing ~30 accounts spins indefinitely, although the accounts are created. Import also
runs the unified-account migration, which re-derives and re-encrypts key material across five
ecosystems; a few seconds per network per account. Reloading during the wait aborts the migration:
the accounts still list afterwards, but signing can fail, and the only recovery is to re-import and
let the affected account migrate again. Reducing the per-keypair cost itself would mean changing
`@subwallet/keyring`, a separate repository.

### Open items

- File a tracker issue if this is to be scheduled; §71 currently has no issue to cite.
- Measure a 30-account import: how much of the wall time is derivation, how much encryption, and
  how much the fixed 1.8 s wait between migration phases.
- Decide whether the duplicate derivation per keypair type is removable without reordering
  `upsertModifyPairs`.
- Decide what the UI owes a user whose migration was interrupted — today nothing is surfaced, which
  is what makes the later signing failure surprising.
