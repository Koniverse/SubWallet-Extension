## B. What the three releases did not move — and the ownership gaps

### No FR changed

All three releases are maintenance: a validator-recommendation improvement inside an
existing earning capability, a chain-list bump, an upgrade-regression fix, a security
fix, and a deprecation cleanup. None materializes a capability the PRD does not already
describe, so the FR table is untouched and the PRD's version header is the only edit —
the opposite of 1.3.83, which shipped a capability with no FR to its name and forced
FR-160 ([D98](../CONTEXT.md)).

### Gap 1 — #5042 had QC stories but no owning feature story → **closed, [US-5.15](../sprints/stories/US-5.15-signing-prompt-mode-confusion.md)**

[US-42.11](../sprints/stories/US-42.11-qc-extension-pr5043-and-issue5045.md) (Extension) and
[US-42.12](../sprints/stories/US-42.12-qc-webapp-pr5043-signing-prompt-security.md) (WebApp)
both QC'd the fix and are `done`, so the *verification* is recorded. The *code* is not owned
by any EPIC-5 or EPIC-8 story:

- **[US-5.10](../sprints/stories/US-5.10-verichains-audit-remediation-hardening.md)** is the
  EPIC-5 remediation cluster, but its table is explicitly *"the findings its acceptance criteria
  name, one for one"* — five rows, five ACs. No AC names #5042, and adding a sixth row would
  break the invariant that story spent a revision establishing. **Do not force-fit it.**
- **[US-8.13](../sprints/stories/US-8.13-payload-decode-error-handling.md)** touches the same
  file (`useParseSubstrateRequestPayload.ts`) but is a different defect — decode *failure*
  handling, shipped 1.3.82 and `done` — and it carries no incremental table.

The fix itself (`5bf7a3b74f`) hardens `RequestExtrinsicSign` so an extrinsic request cannot be
rendered as an inert message, and it ships a spec (`RequestExtrinsicSign.spec.ts`) — which is
exactly the AC-6 shape US-5.10 wants ("each remediation PR includes a regression test").

**Resolved: [US-5.15](../sprints/stories/US-5.15-signing-prompt-mode-confusion.md)** — a new
EPIC-5 story, `done`, `version_shipped: 1.3.85`, EPIC-5 pillar 7 *Signing-prompt integrity*.
Its six ACs are written as claims about the code and each carries a command that fails if the
claim is false ([LESSONS §68](../LESSONS.md)); all six were run, including
`yarn jest …/RequestExtrinsicSign.spec.ts` (1 passed). Neither US-5.10 nor US-8.13 was touched.

**The requirement it defends still does not exist.** NFR-24 (*degrade, never blank*) is the
closest fit and the story is filed against it, but NFR-24 is a reliability requirement. The
property #5042 actually broke — *a signature is only ever produced over the artefact the prompt
displayed* — is written nowhere in the PRD, so nothing would catch the same class again on EVM
`personal_sign`, Bitcoin PSBT or Ledger blind-signing. Minting an NFR is a PRD decision, not a
story decision; recorded in US-5.15 § "Open" and flagged on the NFR-24 row itself.

## D. The board had moved on two weeks

### The question

§C created two sprint files from what the stories declared, and left three past-dated sprints
sitting at `in-progress`. That resolved a `validate` error but not the underlying question:
**what does the team actually think this week is?** The answer is on the GitHub Projects board,
not in the repo.

### The board's week is not the docs' week — but the dates are

**SubWallet.App - Development** (project #2) has a `Week` field of type
`ProjectV2IterationField`, 154 iterations, 7-day, Monday-start. Its **live iteration on
2026-08-10 is `Week 32 - 2026`, starting 2026-08-10**.

That is *not* ISO week 32. The board's numbering runs **exactly one behind ISO**, consistently:

| Board iteration | Starts | ISO |
| --- | --- | --- |
| `Week 27 - 2026` | 2026-07-06 | 2026-**W28** |
| `Week 30 - 2026` | 2026-07-27 | 2026-**W31** |
| `Week 31 - 2026` | 2026-08-03 | 2026-**W32** |
| `Week 32 - 2026` | 2026-08-10 | 2026-**W33** |

The docs use ISO — [sprint-2026-W28](../sprints/sprint-2026-W28.md) starts 2026-07-06 and
[sprint-2026-W31](../sprints/sprint-2026-W31.md) starts 2026-07-27, both matching ISO exactly.
So **the two systems disagree on the number and agree on the dates**, one for one.

> **Do not renumber the docs to match the board.** The docs are internally consistent and
> ISO-correct across 65 sprint files; the board's offset is a configuration artefact. Map by
> **date**, never by the number. The §C reconstruction was right for this reason —
> `sprint-2026-W33` = 2026-08-10 → 08-16 = board `Week 32 - 2026`.

## E. `changelog-coverage.md` asserted 23 citations that do not exist

### What it claimed

The file's own header defines its central bucket: *"An issue is **cited** when a story names its
number (**certain**)"*, and counted **1123** of them. It also said *"Generated — do not hand-edit.
Built by a one-off local helper (kept in the setup scratchpad, not the repo)"* — and that helper
is gone. So the plan from §A was to regenerate it.

### Why regenerating would have made it worse

Rebuilding the parser to the point where it reproduced the committed file exactly — **0 of the
previous 1124 issue rows missing, the only 4 extras being the genuinely new ones from 1.3.84–86** —
took four corrections that are *not* derivable from the changelog:

1. Issue numbers also appear in **paragraph lines**, not only list items
   (`Update \`@subwallet/chain-list@0.2.1\` (#1541):` heads a sub-list) — 8 rows.
2. Four bullets cite a **PR number where the issue is different**: #1384→#1280, #1950→#1949,
   #2590→#2588, #3902→#2902. Two of the four carry a hand-written annotation in the file saying so.
3. `#0` and `#1` are prose (*"address index #0"*), not issues.
4. Numbers linked to another Koniverse repo (ChainList #699/#701/#703) are not our issues.

And attribution turned out to be **curated, not mechanical**: no rule tried against the file
reproduced its issue→story mapping, disagreeing on 26 rows. **A wholesale regeneration would have
overwritten human judgement with a heuristic.** So the file was audited and patched, not rebuilt.

### What the audit found

Running the check the file's own definition implies — *does the named story contain the number?* —
against all 1124 rows:

| | |
| --- | --- |
| Rows whose story contains the number | 1093 |
| Rows naming a story that **does not** contain it, but another story does | **7** |
| Rows in `Cited` that **no story** contains | **23** |

The 23 are all one shape: a bullet naming several issues — *"Support Cardano (#3816, #3924,
#3925, #3942)"* — where the story cites only the first. The siblings were **inferences from the
day the file was written**, filed in the bucket labelled *certain*. Of the 7, two (#3741, #1823)
moved when the audit rounds were split out to US-5.12 — a move this very file documents
elsewhere — and one pointed at **`EPIC-11`**, which is not a story at all.

### What changed

- 23 rows moved `Cited` → `Linked`, keeping their asserted story as *"→ likely US"* — the bucket
  that means *inferred, verify before relying on it*. **Nothing was deleted.**
- 7 rows re-pointed at the story that does contain the number.
- 4 rows added: #5013, #5024 → US-12.6, #5042 → [US-5.15](../sprints/stories/US-5.15-signing-prompt-mode-confusion.md), #5045.
- Counts recomputed: **1128** issues, **1104** cited, **24** linked, across **228 of 306** release
  sections. The previous *"251 Koni releases"* could not be reproduced (228 sections cite an
  issue) and was replaced with the number the checker computes.
- *Assignee resolved: 1109/1124* is **carried, not recomputed** — it needs the tracker, which the
  checker does not read. Marked as such in the file rather than silently restated.
- The header's *"Generated — do not hand-edit"* replaced with what is actually true:
  **generated skeleton, curated content — check it, do not regenerate it.**

### The checker

[`scripts/koni-docs-changelog-coverage.mjs`](../../scripts/koni-docs-changelog-coverage.mjs) —
in the repo this time, beside `koni-docs-check-ids.mjs`. It re-derives nothing; it asks only
whether each recorded claim is still true, and exits non-zero when it is not.

```
$ node scripts/koni-docs-changelog-coverage.mjs
changelog:   1128 issues across 228 of 306 release sections
coverage:    1128 rows (1104 cited, 24 linked)

✓ every cited row names a story that contains its issue number
```

Against the pre-audit file it exits 1 and prints all 34 problems (4 missing rows, 7 stale
attributions, 23 false citations) — the check was run both ways, because a checker that has
never failed has not been tested.

**This is [LESSONS §68](../LESSONS.md) in a second place.** §68 found that 101 of 119 `done`
stories had no command that could refute a ticked box. The same was true of this file's
1123-row *certainty* claim: no command existed, so for 23 rows it was simply false. **A number in
a header is a claim; if nothing can refute it, expect it to be wrong.**
