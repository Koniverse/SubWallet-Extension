### Why not carrying them is the conservative choice

The reflex is to roll unfinished work into the next window. Here that reflex **manufactures a
claim**: a scope table listing eight stories as `review` / `in-progress` in a live window states
that eight things are being worked on. Nothing on the tracker supports that, and these stories have
already been carried once — W31 → W33 — without a single anchor moving.

[2026-08-13 §B](2026-08-13.md) called those statuses *carried claims, not fresh evidence*. Five days
later the same six anchors are still untouched. **At some point a caveat that keeps holding stops
being a caveat and becomes the finding.**

So they keep `sprint: sprint-2026-W33` and their existing statuses, and W34 opens at **3 stories /
7 points** — a small window that is true, rather than a full one that is not.

### This is the second instance, not a new problem

[2026-08-10 §D](2026-08-10.md) left 12 W31 stories as live work in a closed window and called it an
open planning call. This is the same shape again, from the next window along. The recurrence is
what makes it worth surfacing: **the carry-forward is where the docs and the work come apart**, and
one more carry would have hidden it a third time.

Deprioritised, blocked, or dead is a **planning** answer. The docs can show the evidence and decline
to guess; they cannot answer it.

## D. #5058 — a title with an empty body

[#5058](https://github.com/Koniverse/SubWallet-Extension/issues/5058) — *"Support biometric/passkey
login for extension"* — was opened **2026-08-13** by `tunghp2002`. OPEN, no labels, no assignees, no
milestone, and **no body at all**. Nothing in `docs/` mentioned it.

[D108](../CONTEXT.md) says every tracker issue gets a story, so it has one:
[US-5.16](../sprints/stories/US-5.16-biometric-passkey-login.md), `backlog`, no sprint.

**It has no acceptance criteria, deliberately.** There is no requirement to derive them from — ACs
here would be invented, which is the failure this docs layer exists to prevent. The story records
the open questions instead, the load-bearing one being: *does biometry unlock a master password
already held, or replace it as the thing wrapping the key?* Those are different products with
different threat models, and [EPIC-5](../sprints/epics/EPIC-5.md) records the master password as
**non-recoverable by design** — a passkey that replaces the gate rather than fronting it reopens
that decision.

EPIC-5 owns it because that epic publishes the unlock / auto-lock policy (FR-53, FR-55, FR-58) a
biometric path would plug into; EPIC-3 *consumes* that gate rather than defining it.

## E. `check-ids` still exits 1 — the US-42.10 fix was reverted

This was analysed and fixed on 2026-08-13. **The fix is gone** — and so is the §E that recorded
it: [notes/2026-08-13.md](2026-08-13.md) now ends at §D. The working tree came back clean at

discarded before it was ever committed. `check-ids` exits **1** again on the same field:

```
US-42.10  version_shipped: 1.2.44(532)b-v16 — not a release of this product
```

The analysis stands: `1.2.44(532)b-v16` is a real SubWallet-**Mobile** build number in the wrong
*field*. Rule 1b — `version_shipped` names a release of *this* product; rule 4 — EPIC-42 is
`prd_ref: []` so the field belongs empty. Both sibling release-QC pages,
[US-42.6](../sprints/stories/US-42.6-qc-release-extension-v1-3-84.md) and
[US-42.9](../sprints/stories/US-42.9-qc-release-webapp-v1-3-56-0.md), already name their release in
the title and leave it blank.

**Left as-is on purpose.** The revert may have been deliberate, and re-applying a change someone
removed is not a call this pass should make silently. `validate` and `changelog-coverage` both exit
0; `check-ids` is the one red light, on this one field, and it is one line to clear whenever the
call is made.
