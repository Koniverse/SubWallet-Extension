## C. #5062 — a realised loss, and a fix that is only half here

[#5062](https://github.com/Koniverse/SubWallet-Extension/issues/5062), opened 2026-08-24. Now
[US-13.19](../sprints/stories/US-13.19-repoint-kah-pah-usdt-xcm-refs.md), **P0** — the only P0 in
[W35](../sprints/sprint-2026-W35.md).

`statemine-LOCAL-USDt` is the **Kusama-AH-native** USDt (`assets` pallet #1984). `AssetRef.json`
declares an XCM route from it to `statemint-LOCAL-USDt`. That asset **cannot cross the
Polkadot↔Kusama bridge**, so the transfer strands the funds on Polkadot Asset Hub.

> **A user lost 72,614 USDT this way.** Not a latent risk — a realised loss.

Kusama Asset Hub carries two USDt and the wallet registers only the wrong one. `statemine-LOCAL-USDC`
already models the bridged case correctly (`isBridged: true`, `parents: 2`), so **USDt is the odd one
out** — the shape of a data-entry omission, not a design gap.

### The issue and the pull request describe different fixes

This is the part that needed reading twice.

| 2 | Validation logic — `xcm/utils.ts` **+162 / −2**, `Extension.ts` +19, one new string × 5 locales | [PR #5063](https://github.com/Koniverse/SubWallet-Extension/pull/5063) | open, **APPROVED** by `saltict` 08-24 |

## D. #5058 — the code answered the question the issue never did

On 2026-08-18 [US-5.16](../sprints/stories/US-5.16-biometric-passkey-login.md) was written as a
placeholder for an issue that was a bare title, and its load-bearing open question was:

> Does biometry **unlock a master password already held**, or **replace it** as the thing wrapping
> the key?

[PR #5061](https://github.com/Koniverse/SubWallet-Extension/pull/5061) opened 08-20 — 3 commits,
**+1035 / −49** across 20 files. **The issue body is still empty**; the branch settles it. Read from
the source rather than inferred from file names:

```
wrapWalletPassword (password, encodedSecret)
  → crypto.subtle.encrypt({ AES-GCM }, key, plaintext = password)
```

The key is imported from the passkey **WebAuthn PRF extension** output; `enrollPasskeyUnlock()`
stores `{ciphertext, nonce, credential, input}` and `rotatePasskeyUnlockSecret()` re-wraps.

**It wraps, it does not replace.** The master password stays the root of custody, so EPIC-5's
*non-recoverable by design* decision is **not** reopened — which was the whole reason the question
was load-bearing. Enrolment lives in Settings → Security, consistent with an opt-in layer over the
existing gate.

Story moved `backlog` → `review`, points 1 → 8, and it now carries **seven acceptance criteria
derived from the code** — legitimate because they describe what was built and are refutable against
the branch, unlike ACs invented from a blank issue. None ticked: the PR is unmerged and has **0
reviews**.

**AC-3 is the one to watch** — the master password must still unlock when no passkey is enrolled or
the authenticator is gone. That is the path by which an unlock convenience becomes a way to lose a
wallet. It does ship **2 spec files**, which is more than [US-12.22](../sprints/stories/US-12.22-nominator-fast-unbond-duration.md)
managed.

## G. Later the same day — #5064 got a PR, and it answered its own empty issue

Section E recorded #5064 as a title with an empty body and gave it a `backlog` placeholder with no
acceptance criteria. **Hours later
[PR #5065](https://github.com/Koniverse/SubWallet-Extension/pull/5065) appeared** — 1 commit
(`f66902bab9`), **+198 / −14** across 9 files, 0 reviews.

This is the second time this month the pattern has run: an issue with nothing in it, then a PR that
explains what the issue was for. #5058 took a week; #5064 took a day.

### What the code says

The load-bearing line is a comment in the diff itself:

> *Root claims redeem the basket of a netuid 0 position, subnet (alpha) positions have nothing to claim*

`claimReward: true` in `native-staking/tao.ts` (**+162 / −4**), `claimReward: false` in `dtao.ts`.
New chain reads: `betaBasketRuntimeApi.getRootBasketOwed()` / `getRootBasketPositions()`, with
`subtensorModule.rootClaimableThreshold` behind `getRootClaimThreshold()`.

Three of [US-12.23](../sprints/stories/US-12.23-bittensor-manual-claim-native-staking.md)'s four open
questions are answered by that: it is **root-network TAO, not subnet/alpha**, which means the overlap
worry with [US-12.6](../sprints/stories/US-12.6-bittensor-dtao-subnet-staking.md) is a non-issue —
the `dtao.ts` edit exists precisely to say alpha positions have nothing to claim. Story moved
`backlog` → `review`, P3 → **P2**, 1 → 5 points, into [W35](../sprints/sprint-2026-W35.md).

### The unanswered question is still the sharp one

v1.3.86 **removed** a deprecated Bittensor root claim type (#5045,
[US-12.21](../sprints/stories/US-12.21-earning-fixes-recovered-from-uncategorized.md)). This PR adds
a root claim path on a **different** runtime API, so on the evidence it replaces rather than revives
— but neither the PR nor the issue says so, and that is precisely what a reviewer should confirm.

### Two ways this breaks without anyone noticing

- `RootClaimableThreshold` is a substrate-fixed **`I96F32`**: the raw bits carry 32 fractional bits
  and must be scaled by `2^32`. Read unscaled it is wrong by **nine orders of magnitude**.
- When the `rootClaimableThreshold` query is absent, the handler falls back to
  `DEFAULT_ROOT_CLAIM_THRESHOLD` = `500000` rao (0.0005 TAO).

Both fail by producing a **plausible wrong number**, not an error — and **the PR ships no test**.
AC-3 and AC-4 on the story name them; both are unit-testable without a chain.
